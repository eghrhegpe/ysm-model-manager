## 2. 决策（Decision）

### 2.1 🔴 严重债务（影响正确性或运行时行为）

#### D1：`nav:change` vs `nav:changed` 事件名漂移 —— 真实 bug

**现象**：`app-nav` 发射 `nav:change`，但 `page-store.ts` 订阅 `nav:changed`。

```
app-nav/index.ts:46   bus.emit("nav:change", { page })   ← 初始恢复发射
app-nav/index.ts:190  bus.emit("nav:change", { page })   ← 点击导航发射
page-store.ts:68      bus.on("nav:changed", ...)         ← 唯一订阅 changed
app-content/index.ts:93 bus.on("nav:change", ...)        ← 唯一消费 change 的组件
```

**根因**：`app-content` 订阅 `nav:change`，渲染完成后转发 `nav:changed` 给 `page-store`。如果 `app-content` 未挂载（懒加载场景），`page-store._currentPage` 拿不到初始页，导航高亮静默丢失。

**处置**：统一为单一事件名 `nav:changed`，`app-nav` 两处 emit 全部改为 `nav:changed`，删除 `app-content` 的转发层。

**优先级**：P1（运行时行为 bug）。

---

#### D2：`loading:start` / `loading:end` 事件孤儿

**现象**：`loader.ts:30` emit `loading:start`，`loader.ts:140` emit `loading:end`。生产代码无消费者（仅 `loader.test.ts` 测试订阅）。

**处置**：删除这两处 emit（或写入 bus 事件常量表并标注废弃）。

**优先级**：P3（死代码清理）。

---

#### D3：`web-fs.ts` 上帝模块（1236 行，16 段职责）

**现状**：一个文件承载 IDB 扫描、导入分组、FSA 授权、NBT meta、搜索、重命名、删除、移动、binding 装配。虽已加目录注释（本次提交），但物理行数未减。

**处置**：
- 短期：保留目录注释，等真实消费边界信号出现（如某消费者只需导入分组不需要 readers）再切
- 中期路线图：
  - `web-fs-auth.ts`（FSA 授权簇，~100 行）
  - `web-fs-scan.ts`（扫描/搜索/列表，~350 行）
  - `web-fs-mutate.ts`（重命名/删除/移动，~250 行）
  - `web-fs-import.ts`（导入分组，~200 行）
  - 主文件只留 key 规约 + mainFileRank + binding 装配

**优先级**：P2（维护负担，无运行时风险）。

---

#### D4：`web-fs.ts` 反向依赖 UI 层（违反分层原则）

**现象**：
```ts
import { t } from "../core/i18n/t.ts";   // backend → i18n
import { bus } from "../bus.ts";          // backend → 事件总线（1 处 loading:end 孤儿）
```

**处置**：将 i18n 键名作为错误返回值返回，由 browser-adapter 之上的调用方负责翻译。`bus` 依赖仅在 loading:end 孤儿处，删除 emit 即可消除。

**优先级**：P2。

---

#### D5：`mount-preview-core.ts` 上帝函数（722 行，rAF 闭包捕获 ~30 变量）

**现状（已拆分，2026-08-17）**：原 707 行拆为 537 行主文件 + 4 个模块文件。animate 循环因与状态耦合深暂留主函数（非阻塞项，后续可独立）。

**已落地**（commits `946728a4` / `25de7e7b` / `49c346c8`）：
- `postprocessing.ts`（67 行）：PostprocessingManager，postprocess composer 生命周期从此处而非 core
- `cleanup-3d.ts`（118 行）：fullCleanup + safeDisposeMat
- `switch-preview.ts`（178 行）：switchToSession + syncLightTargetFromContent
- `input-and-animation.ts`（120 行）：bindInputHandlers
- `mount-preview-core.ts`：537 行，保留 mount3D 主入口 + animate 循环

**未完全达成**：原始方案中 `MountCore`/`PreviewUI`/`PreviewLifecycle` 三段式未采用，改为按职责边界（cleanup/switch/input/postprocessing）拆分，更贴合实际代码结构。

**优先级**：P1（可维护性瓶颈，3D 预览是核心用户路径）。

---

#### D6：Go `threejs/spec.go` `buildModelGroup` 299 行怪物函数

**现象**：模型分组构建 + UV 分配 + 顶点合并 + 纹理索引映射全塞一个函数，无注释分段。同类问题：`buildCubeMeshData` 210 行、`ysm/summary.go` `ExtractYsmSummary` 239 行。

**处置**：拆为 `assembleVertices / assignUVs / packIndices / mergeBones` 四个纯函数；`buildCubeMeshData` 拆出 `transformCube / layoutUV / computeNormals`。

**优先级**：P2。

---

#### D7：`import-queue` 四文件分散幽灵上帝对象（~1178 行）

**现状**：通过 5 个 `{ get, set }` live ref 中转耦合，`bindButtonEvents` 签名膨胀到 18 参数。数据层仍夹着 60%+ DOM 操作（`el.style.display = ...`、`textContent = ...`）。

**处置**：收敛为 `currentState: Ref<ImportQueueState>` 单一对象，5 个代理合并为 1 个，参数数砍半。

**优先级**：P2。

### 2.2 🟡 中等债务（维护负担）

#### D8：`voxel-colors-data.ts` 1632 行 / 61KB 静态对象

import 时即实例化，bundle 冷启动固定占用。纯数据，建议改 `.json` 导入（vite 已有此范式）或懒加载。

**优先级**：P3。

---

#### D9：`download-queue` 三文件 905 行（拆分后膨胀）

原始 829 行拆为 3 文件后反而膨胀 1.1×——每文件保留 re-export 头、接口声明、注释块。

**处置**：合并为单文件 + 内部分区注释（与 web-fs 方案一致）。

**优先级**：P3。

---

#### D10：`app.ts` 桌面/Web 双路径与 `platform.ts` resolveWebMode() 口径漂移

**现象**：`app.ts:31-57` 自造分支，不统一走 `platform.ts` 的 Tier 判定。

**处置**：桌面路径只走 `window.go.main.App`，Web 路径一律 `resolveWebMode()` + browserAdapter。

**优先级**：P3。

---

#### D11：Go `importer.registry` 普通 `map` 无锁

对比 `download.fileLocks` / `scanner.scanCache` 用 `sync.Map`，`importer.registry` 并发写入会 panic。

**优先级**：P2（并发安全）。

---

#### D12：`configFunc` 变量散落在 4 个包重复声明

`download/fileops/logs/scanner` 各有一份 `var configFunc func() types.AppConfig`。已收敛到 `go/config` 单持有点（一个 `atomic.Pointer` 存 provider 函数），四包不再各留副本。

**存放分层说明**：原设想「收敛到 `go/internal/app/AppContext`」分层不可行——这四个是下游纯 Go 包，`internal/app` import 它们，让它被反向持有配置源会成循环依赖。收敛点落在更下的共享包 `go/config`，由 `internal/app` 在 ServiceStartup 经 `config.Set(a.LoadAppConfig)` 填充，四包 helper 读 `config.Get()`。

**实现要点**：存 provider 函数而非配置快照指针，复刻原「每次读取现拉」语义——`SaveThresholds` 等运行期写盘后阈值立即可见，行为零漂移（ADR-062）。`atomic.Pointer[Provider]` Store/Load 原子完成，消除并发读写数据竞争（audit-r3 P3-2）；`go/config` 含 `-race` 并发测试。

**优先级**：P3。

---

#### D13：bus 事件命名三套风格混用

`kebab:kebab`（`toast:show`）/ `noun:verb`（`instance:export-list`）/ `verb-noun`（`ctx:show`）/ 多级冒号（`sync:download:done`）。

**处置**：统一为 `scope:action`，事件名集中声明在 `core/bus-events.ts` 常量表，`bus.emit / bus.on` 改为引用常量。

**优先级**：P3。

---

#### D14：测试钩子命名不统一

`__resetWebLogStateForTest`（双下划线）vs `_resetDBForTest`（单下划线）vs `setStatsRunnerForTest`（无下划线）。统一为 `__...ForTest` 命名规范。

**优先级**：P3。

---

#### D15：pack-meta.ts 4 个导出过宽

`findZipEntry / parsePackMetaJson / packPngToThumbnail / parseShaderpackLang` 只有 `web-fs.ts` 一个消费者，改 non-export。

**优先级**：P3。

#### D21：`window.applyTheme` 跨 Shadow 边界暗契约（6 处）

**现象**：`app-content/settings/theme.ts` 共 6 处调用 `window.applyTheme?.(themeName)`，绕过 bus 直接用 `window` 全局变量传参。违反 `frontend/AGENTS.md`「跨 Shadow 边界传数据用 `bus.emit`」约定。

**同类**：
- `app-preview/zoom.ts` L76-85 直接 `window.addEventListener("pointermove|up|cancel")`，脱离组件生命周期
- `app-content/site/events.ts` L330 注册 `window.addEventListener("storage")`（已随 `_storageSyncFn` 清理，风险中等）

**处置**：改为 `bus.emit("theme:change", { name })` 或注册到 `registry` 的单点主题服务。

**优先级**：P2（跨边界反模式，维护风险高）。

---

#### D22：`app-content` 多层补丁堆叠

**现象**：`app-content/index.ts:173` 注释自证「app-content 常驻不卸载，多次访问 repository 的 dedup/oldest/import/recycle 会让 repo:rtype-changed 监听与 cleanup 跨访问累积」。已通过 `_render()` 内清空 `_unsubs` 修复，但代码已带 4 层 P2/P3 补丁注释。

**处置**：重构为「每页独立生命周期管理器」，切页即 dispose 旧页所有订阅，不再手动堆补丁。

**优先级**：P2。

---

#### D23：`window.open()` 在 Shadow 组件中直接调用

**现象**：`app-tree/events.ts` L230、`app-content/settings/init.ts` L289 直接跨 Shadow 调用宿主 API，绕过 bus / 注册表；桌面 Wails 与网页模式（ADR-049）行为分叉。

**处置**：封装 `openInBrowser(url)` 桥接函数，桌面走 Wails API，网页走 `window.open()`。

**优先级**：P2。

---

#### D24：`tpl.ts` 命名语义模糊 + i18n 覆盖率不足

**现象**：
- `app-content/` 下 10+ 个 `tpl*.ts` 文件混排 HTML 模板生成器与业务逻辑，新接入者需逐个读才知边界
- `app-sidebar/tpl.ts` L13-16 有 4 处运行时中文硬编码（`"资源包"` / `"光影包"` / `"蓝图"` / `"投影文件"`）未走 `t()`，违反 ADR-045
- views/ 52/101 ≈ 51% 源文件导入 `t()`，i18n 覆盖率偏低

**处置**：`tpl.ts` → `*-html.ts` 重命名（5 组件同步）；4 处硬编码改 `t("rtype.pack")` 等并补全三个语言包。

**优先级**：P3。

## 3. 后果（Consequences）

### 正面

- **ADR-034 历史债大部分已闭环**：方向一/二/三已落地，仅方向五 P1 残留（wasm_decoder 硬编码路径）
- **`web-fs.ts` 目录注释已加**：16 节快速跳转导航降低阅读成本，为零成本改进
- **Go 层测试覆盖率良好**：122 test / 71 source（1.72:1），panic = 0，容器层统一度 = 100%
- **views/ 组件生命周期规范**：9/9 组件都有 connectedCallback/disconnectedCallback 配对
- **no-platform-assumption 前端**：`navigator.platform` / `process.platform` 调用 = 0 处

### 负面

- **D1（nav:change 漂移）是运行时 bug**：懒加载场景下导航高亮静默丢失
- **D5（mount-preview-core）是可维护性瓶颈**：3D 预览是核心用户路径，722 行单函数修改代价高
- **D3（web-fs.ts）是累积风险**：虽已加目录注释，但物理行数未减，PR diff 爆炸仍会发生

### 已知遗留

- `wasm_decoder.go:28-29` 硬编码开发者本机 node.exe 路径（ADR-034 方向五 P1）
- `litematic/gen` 127 行生成代码零测试（可豁免）
- `nav:change` vs `nav:changed` 漂移需在下一轮修复
