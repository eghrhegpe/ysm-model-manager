## 三、诡异决策 + 诡异实现清单

### 1. ADR-079：三端 COOP/COEP 注入 + 重编译上游 WASM ⚠️ 诡异度：高
- **决策方案**：单模型解码多线程 = 三端 COOP/COEP 注入（网页 SW credentialless / 桌面 Go build tag 中间件 / Android `shouldInterceptRequest`）+ 重编译上游 `-pthread -sUSE_PTHREADS=1`
- **代码实现**：M1-M4 全部落地：
  - M1：`frontend/public/sw.js` + `frontend/src/workers/coi-sw.ts`（SW 补 COOP/COEP 头）
  - M2：`internal/app/coi_middleware.go` + `mpr_off.go` / `mpr_on.go`（`-tags mpr` build tag 门控）
  - M3：`frontend/src/wasm/ysm-glue-data-mt.js`（pthread 版 WASM 数据）
  - M4：`frontend/src/workers/stats.worker.ts:120-127`（crossOriginIsolated 分支 → pthread/单线程自动降级）
- **诡异度评估**：**⚠️ 高**。为了解锁 SharedArrayBuffer（让单模型解码快 1.5-2x），三端各写一套截然不同的 COOP/COEP 注入机制，还要重编译上游 C++ 解析器产出双 WASM 产物。典型的"为治一时之病（单模型解码慢）而埋更深的隐患（三端耦合 + 双产物体积增长 + SW 首次导航需 reload）"。违反"通用化、统一"准则——同一个需求三种实现路径，且每种都绕过了平台原生能力。

### 2. ADR-042：内嵌第三方 molangjs 源码 ⚠️ 诡异度：中
- **决策方案**：npm molangjs 包因 ESM/CJS 混用在 Node 测试环境连续报错 → 源码内嵌到 `frontend/src/utils/animation/molang-lib/`
- **代码实现**：确认 `molang-lib/` 目录存在（保留 JannisX11 molangjs MIT 原始版权头）
- **诡异度评估**：**⚠️ 中**。为绕过 npm 包模块系统不兼容而内嵌第三方源码。虽保留版权头（合规），但违反了"不维护第三方库源码"的常规工程实践。若 molangjs 上游更新需人工同步。属于"为治环境兼容之病而埋维护之隐患"。

### 3. ADR-173：GUI→CLI 参数桥 4 次格式转换 + ParamSpec 白名单 ⚠️ 诡异度：中
- **决策方案**：GUI→CLI 参数经 4 次格式转换（`Record<string,string|number|boolean>` → `map[string]interface{}` → `[]string` → `flag.FlagSet`），引入 ParamSpec 白名单协议做序列化控制
- **代码实现**：`go/cli/registry.go:39-45` `ParamSpec` 结构体存在（Key/Type/AllowEmpty），`CliCommand.Params` 携带规格，`GetAllowedCommandSpecs` 存在，`paramspec_test.go` 测试覆盖。但 ADR 自身承认 A3 被降级："仅注释契约消除，不做运行时规格透传"——前端零运行时消费 ParamSpec。
- **诡异度评估**：**⚠️ 中**。4 次格式转换本身已是设计债务（参数知识散落三处注释、空串/0/false 丢弃语义）。ParamSpec 白名单是正确方向，但 A3 降级后前端不消费——协议层只做了一半，运行时收益全部在 Go 侧兜底。属于"方向正确但执行打折"。

### 4. ADR-126：菜单 Schema 终态——4 子步渐进式声明式化 ⚠️ 诡异度：中低
- **决策方案**：状态层泛化（P4-A）→ 面板 schema 化（P4-B）→ 可见性谓词化（P4-D）→ dockGroup 解耦（P4-C），4 个独立子步，每子步独立 commit
- **代码实现**：P4-A（状态层泛化）已落地（`preview-state.ts` 7 域路径表），P4-B/P4-C/P4-D 部分落地。`collectVisiblePredicates()`、`MenuControlDef.settingsOrder` 等机制存在。
- **诡异度评估**：**🟡 中低**。方案本身是合理的渐进式重构（治"4 类病根"：dockGroup 1 字段 4 职责 / roleDetailView 万能容器 / model/motion 交叉渲染 / fill3DPanel 命令式渲染），但 4 子步相互依赖、排序讲究，每子步独立 commit 增加维护成本。属于"为治结构病而做的手术"——合理但代价不小。

### ADR 整体可信度判断：**中**

大部分 ADR 的决策方向与代码实现一致，但存在三类系统性问题：

1. **命名偏差**（ADR-122 / ADR-068）：声明的组件名与代码实际名称不符（`MdMmBuildCtx` → `BuildCtx`、`ContainerReader` → `Reader`）。这是 ADR 写作时凭记忆写名字而非 grep 确认导致的。
2. **状态字段滞后**（ADR-059 / ADR-094 / ADR-004）：被后续 ADR 部分推翻但状态未更新。ADR 状态只有四态（✅ / 🔄 / 🧊 / ❌），无法表达"已采纳但部分被后续 ADR 推翻"这种中间态。建议引入 `🔁 部分取代` 状态或在状态行追加注记。
3. **路径漂移**（ADR-127 / ADR-068）：声明路径与实际不符（`utils/3d/state/` → `preview-3d/state/`）。这是目录重组后 ADR 未同步导致的。

**亮点**：ADR-103 §0 自带"后续变更记录"承认过时——这是好习惯。ADR-102 诚实标注与 ADR-059 的关系——也是好习惯。建议推广为所有被后续 ADR 影响的 ADR 都加"演进注记"段。

**最值得关注的设计债务**：ADR-079 的三端 COOP/COEP 注入方案——为解锁单模型解码 1.5-2x 加速，付出了三端耦合 + 双 WASM 产物 + SW reload 的体验代价。若未来有平台原生多线程解码方案，应优先切换。
