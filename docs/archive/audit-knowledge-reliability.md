| 维度 | 判定 | 依据 |

## 二、闸门有效性：变异测试（决定性证据）

门禁"全绿"最可疑的解释是"检查器空转"。构造变异体直接证伪：

在 `_knowledge_audit_tmp/mutant/` 拷贝 2 张卡，注入 3 处破坏（指向不存在的路径 / 指向不存在的锚符号 / 注入硬编码行号），用 `--kc-dir` 隔离模式跑真检查器：

```
ERROR : 3     ← source_files 不存在 1 + 锚文件不存在 1 + 锚符号失效 1
WARN  : 2     ← 正文硬编码行号 L123 / L180
退出码 1（可接 CI 卡点）
```

**3 处破坏全被抓出，退出码非 0。** 闸门是真的，不是假绿灯。

补充：检查器本身有测试覆盖（`tests/test_check_knowledge_content.ts` 等 10+ 个 `check-knowledge-*` 测试文件），不是裸奔的脚本。

## 四、三个真实盲区（闸门看不见的地方）

### 4.1 冒号形行号：检查器完全没有这个分支 ⭐

把 `check-knowledge-drift.ts` L811 的 `BODY_LINE_RE_FINAL` 原文抠出来直跑（修正 `g` 标志 `lastIndex` 污染）：

| 形态 | 结果 |
|---|---|
| `L164` / `L100-107` / `983 行` / `10 个能力` / `247 行` / `57 行` | ✅ 6/6 命中 |
| `resource_bindings.go:27` / `instance.go:225` / `queue.go:254` | ❌ 漏检 |
| `litematic-adapter.ts:263` / `watcher.go:268-280` | ❌ 漏检 |
| `core.ts:506` / `instance-ops.ts:73-80` | ❌ 漏检 |

正则三个分支（`L\d+` / `\d+ 行` / `\d+ 个X`）**没有一个覆盖冒号形**，而 `文件.ext:行号` 恰是仓内最主流的硬编码写法。语料实测：

- 9 张卡共 **18 处**冒号形行号，全部在检查器射程之外
- 重灾区：`app-content-diagnostics.md` ×6、`preview-menu.md` ×3、`go-repoaudit.md` ×2、`go-ts-golden.md` ×2

**这就是"0 WARN 与 35 处实际违规共存"的机理。** 豁免设计本身没问题（`ADR-NNN Lx`、`L0` 游戏层级、`≤~–≤` 前缀历史值都正确豁免），缺口只在冒号形。修法很轻：正则加一个分支 `[\w.-]+\.(?:ts|tsx|go|js)\s*:\s*L?\d+`。

### 4.2 裸文件名引用：55% 的机制引用零校验

`check-knowledge-content.ts` 的锚定正则**要求路径含 `/`**（与纯反引号符号、中文反引号短句区分）。于是：

| 形态 | 数量 | 是否校验 |
|---|---|---|
| 显式锚定（含 `/` 的完整路径） | 694 处 | ✅ 校验 |
| **裸文件名**（`preview-state.ts`、`render.ts`…） | **839 处 / 402 个文件** | ❌ **零校验** |

裸文件名占全部机制引用的 **55%**。TOP 高频：`index.ts` ×27、`tpl.ts` ×14、`render.ts` ×12、`events.ts` ×12、`schema.ts` ×11、`mount-preview-core.ts` ×6。
这些"必须走 X 的 Y"式散文声明，重构改名后**静默失效，无人报错**。

### 4.3 时间维度：44/191 卡源码改动晚于卡更新

无任何检查器覆盖这个维度（它们查符号存在性，不查散文时效性）：

| 指标 | 数字 |
|---|---|
| 滞后卡 | **44 / 191（23%）** |
| 新鲜卡 | 147 / 191（77%） |
| 滞后最久 | `go-testutil.md` 27 天、`android-bridge.md` / `dialog-batch-rename.md` / `event-bus.md` 26 天 |

注意：这是**信号**不是定罪——源码改动可能不涉及卡的内容。但 `check-knowledge-drift --affected` 只能在提交时按 staged 文件提示，跨会话/他人提交的漂移会累积到下一轮人工才暴露。

## 六、锐评

**能信**：路径不会断、锚点不会断、ADR 编号不会错。这三条是机器可证的硬承诺，而且闸门是变异测试过的真闸门——不是"文档写得勤"的自觉，是有 CI 卡点的约束。

**不能信**：正文里"机制靠 X 函数实现"这类散文。55% 的机制引用是裸文件名（零校验），最主流的硬编码形态 `文件:行号` 检查器根本没有这个分支（18 处违规全在盲区），加上 23% 的卡源码已领先于卡更新。**文字会偷懒，机器看不出来。**

**一句话**：这个知识库的可靠性上限不在"卡写得够不够好"，而在"闸门够不够亮"。承重墙（frontmatter + 锚点 + ADR）已经做到了 fail-closed 且有测试守护；散文层还停在"建议"。真正的杠杆点是**把 `文件:行号` 分支和裸文件名锚定补进正则**——两处改动，能让现有闸门从"守路径"升级到"守一半的文字"。

**引用规范**：正文一律写「`文件|符号`」而非行号（ADR-162 精神）；判断机制现状只认源码树，不认 ADR 背景与卡正文。

**整改方法论（可复用）**：失准声称的修法不是把行号改成正确行号，而是**把散文升格为 `invariant_anchors`**——散文声称无锚故漂移不阻断，锚失名即 ERROR。这是本次两处失准卡共同的根因，也是「散文层零校验」这个缺口唯一经济的补法（逐条给 839 处裸文件名补锚不现实，但给承重墙机制补锚可行）。

**未闭环（留给后续）**：
1. 14 张卡的正文冒号形行号仍留 WARN（闸门已可见，非阻断）——改写需逐条查真实符号，风险高于收益，建议按需分批。
2. 839 处裸文件名机制引用（占机制引用 55%）零校验——正则无法可靠判断裸文件名是否指向「含该机制」，需人工升格锚。
3. 23% 卡的源码领先于卡更新——属 `--affected` 主动匹配范畴，非检查器缺分支。
4. `extensibility-round2` 同时 `status: active` + `affected: false`：它被 routes-quick 注入（一跳层），却退出 `--affected` 匹配——本次失准静默 6 周的直接原因。属卡元数据语义问题，未擅改，待评审拍板。
