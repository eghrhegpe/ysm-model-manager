## 一 · 一条长在别人身上的胳膊

模型加载完了。渲染也成功了。没有报错，没有警告，控制台干干净净。

只是那条胳膊——**长在了肩膀外面十几个像素的地方**。

袖子跟着一起飘出去，像被风吹跑却忘了脱手的衣服。头发没有展开，帽子扁在头顶，裙子挤成一团。

`app-preview` 把画面举起来给 `threejs` 看：「你渲的。」

「我按你给的坐标渲的。」`threejs` 说。

「那坐标是错的。」

「那也不是我给的。」

两个都没说谎。这类 bug 最难缠的地方就在这里——**每一层都忠实地执行了上一层交给它的东西**，而错误早在谁都没注意的地方就已经完成了。

---

## 二 · 一张只有一个抽屉的柜子

`spec.go` 里有一张 map。它的活儿很简单：记住每根骨骼的支点（pivot）。

```go
pivots := make(map[string]vec3)
for _, b := range model.Bones {
    pivots[b.Name] = vec3{-b.Pivot[0], b.Pivot[1], b.Pivot[2]}
}
```

单文件模型的时代，这张 map 从没出过错。骨骼名唯一，一个名字一个支点，清清楚楚。

问题出在**多 geometry 文件**上。`main.json` 有一根叫 `arm` 的骨骼，`arm.json` 里也有一根叫 `arm` 的骨骼。它们是两个不同文件里的、两个不同位置上的、两根不同的骨头。

而这张 map 只认名字。

于是第二次写入覆盖了第一次。`arm.json` 的支点被写进去，或者反过来——取决于谁后加载。然后所有立方体都去查这张 map：

```go
bp := pivots[b.Name]
buildCubeMeshData(c, bp, ...)   // arm.json 的 cube，用了 main.json 的 pivot
```

**一根骨头，绕着另一根骨头的支点旋转。**

这就是那条飘出去的胳膊。它没有错位，它只是**在围绕一个不属于它的中心点做正确的旋转**。

同一个坑还有第二层。ZIP/7z 的解析路径上，有一段去重逻辑：

```go
for _, b := range g.Bones {
    if !seen[b.Name] {
        geo.Bones = append(geo.Bones, b)
    }
}
```

同名骨骼被 `seen` 拦下，连带它身上的所有 cube 一起被丢掉。头发没展开、帽子扁了、裙子挤成一团——不是渲染失败，是**那些立方体根本没被送进渲染管线**。它们在解析阶段就被当成重复品扔了。

第三层更安静：`Bone2D` 结构体里，压根没有 `Rotation` 字段。

```go
type Bone2D struct {
    Name   string
    Parent string
    Pivot  [3]float64
    // Rotation 不存在
}
```

不是解析失败。是这个数据**从来没有被表达过**。源文件里写着旋转角度，解析器读到它，然后——因为没有地方放——把它丢了。丢得如此彻底，以至于下游没有任何人知道曾经有过这个字段。

## 三 · 让每个人拿自己的中心

修法分成三刀。

第一刀，map 改为**首次写入优先**，不再被后来者覆盖：

```go
if _, exists := pivots[b.Name]; !exists {
    pivots[b.Name] = vec3{-b.Pivot[0], b.Pivot[1], b.Pivot[2]}
}
```

第二刀更狠——**不再共享这张 map**。cube 计算直接用当前骨骼自己的 pivot：

```go
bpSelf := vec3{-b.Pivot[0], b.Pivot[1], b.Pivot[2]}
```

一根骨头绕自己的支点转。听起来是句废话，但它此前确实不成立。

第三刀，`Bone2D` 补上 `Rotation [3]float64`，`spec.go` 把欧拉角转成四元数：

```go
eulerToQuaternion(-b.Rotation[0], -b.Rotation[1], b.Rotation[2])
```

注意那两个负号。它们不是笔误，是 Bedrock 坐标系与 Three.js 坐标系之间的换算——X 轴反向。ADR-004 后来把这条口径正式写死：**坐标系转换只允许发生在解析边界上，一旦进入 `threejs` 包，就必须已经是 Three.js 的世界观。**

而 ZIP/7z 那段 `seen` 去重，被整条删掉，改为全追加：

```go
geo.Bones = append(geo.Bones, g.Bones...)
```

去重交给下游的 `threejs.Build()`。理由很简单：**解析层不该做取舍**。它的职责是把源文件里有的东西完整搬过来，谁重复、谁该留，是构建层的判断。解析层一旦开始「聪明」，丢掉的数据就再也找不回来了。

## 四 · 透明的墙

胳膊回到肩膀上以后，第二个问题浮出水面。

透过衣服能看见皮肤——这本身没问题，衣服有透明区域。但**透明区域会挡住它后面的东西**。空洞、遮挡、忽隐忽现，取决于摄像机绕到哪个角度。

`threejs` 查了自己的材质配置：

```js
transparent: true    // depthWrite 默认 true
```

于是深度缓冲区里，那些完全透明的像素也堂堂正正地占了位置。它们对屏幕没有任何贡献，却对深度测试拥有完整的否决权。后面的物体来敲门，深度缓冲说：这儿有人了。

「那把 `depthWrite` 关掉？」

关掉之后更糟——透明物体全部盖在所有东西之上，前后顺序彻底错乱。半透明渲染的经典陷阱：**你只有两个选项，一个错在深度，一个错在顺序。**

除非，你根本不需要半透明。

Minecraft 像素风贴图是**二元透明度**——一个像素要么全透，要么全不透，没有中间态。既然没有中间态，就不需要混合，也就不需要 `transparent`：

```js
const mat = new THREE.MeshBasicMaterial({
  map: cubeTex,
  alphaTest: 0.5,          // alpha < 0.5 直接丢弃，不进管线
  side: THREE.DoubleSide,
  // 无 transparent → 走不透明通道，深度缓冲正常工作
});
```

`alphaTest` 不是"更好的透明"。它是**取消了这个问题**。透明像素在片元着色阶段就被丢弃，从来没有进入过深度缓冲，于是深度缓冲没有理由说谎。

## 尾声

`threejs` 后来常想起那条飘在半空的胳膊。

它当时渲得非常认真。顶点、法线、UV，一个都没错。矩阵乘法算了成千上万次，每一次都精确到浮点数的末位。它把一根骨头以完美的精度，绕着一个错误的中心旋转了完美的角度。

**精确和正确是两件事。**

那张按名字索引的 pivot map 也是。它没有 bug——它完美地实现了「按名字查支点」这个契约。问题在于这个契约本身建立在一个假设上：**名字是唯一的**。

假设从来不会自己报错。它只会在某一天不再成立，然后让所有依赖它的正确代码，一起产出错误的结果。

而 `seen` 那段去重更让它后怕。那不是算错，那是**丢弃**。算错的东西还有痕迹可查，丢掉的东西连尸体都没有。头发不展开的那天，没有任何日志记录过「有 47 个 cube 被跳过了」。它们只是不在那儿。

调试丢失的数据，比调试错误的数据难一个数量级。因为你得先意识到**本该有东西在那儿**。

**缝**：解析层的「聪明」是下游的失明。任何在数据入口处做的取舍——去重、跳过、静默降级——都会让后面所有人失去发现问题的机会。入口只应负责搬运，判断留给看得见全局的人。

---

**教训**：共享的索引会被同名者覆盖，解析层的去重会让数据死无对证。
