> 时间线标签：vol-4
> 对应真实事件/代码改动：ADR-028（安装器链接模式原子替换与 relink 回滚保护，commit `5c83738`）、bug-chronicle #8（安装模型失败「源文件不在仓库目录内」）

---

## 一 · 更新了，但没更新

用户下载了模型的新版本，点了安装。

进度条走完。日志写着「安装成功」。没有报错。

然后游戏里加载出来的，还是旧版本。

用户又下了一次，又装了一次。还是旧的。第三次，他开始怀疑是自己下错了文件——毕竟系统说了成功，三次都说成功。

`installer` 那边的记录也很清白。它确实执行了安装流程，确实走到了返回 `nil` 的那一行。

问题在于它是**从哪一行返回的**。

```go
if _, err := os.Lstat(dst); err == nil {
    return nil   // 目标已存在，跳过
}
```

目标已存在，即视为完成。

这行代码的本意是幂等——重复安装不该报错。逻辑上无懈可击：既然文件已经在那儿了，还装什么？

但它漏了一个问题：**在那儿的，是不是我要装的那个。**

---

## 二 · 三种「已存在」

`installer` 后来被迫把这个问题拆开看。「目标已存在」这五个字，底下藏着至少三种完全不同的状况：

| 情形 | 磁盘上是什么 | 该做什么 |
|------|------------|---------|
| 同一个文件 | 已经是指向源的有效硬链接 | 什么都不做，真幂等 |
| 旧版本 | 上一次安装留下的、指向旧源的链接 | 必须替换 |
| 独立副本 | copy 模式遗留的实体文件，与源无任何关系 | 必须替换 |

三种情况在 `os.Lstat` 眼里长得一模一样：**存在**。

于是后两种被当成第一种处理了。更新模型永远命中旧文件，relink 遇到 copy 模式遗留的副本时也不会真的建立链接——它只是看见那儿有东西，然后说「好了」。

`installer` 管这个叫「假成功」。它比失败难查得多。失败会留下错误信息，会有人来看；假成功什么都不留，它甚至会给你一条绿色的日志，鼓励你相信一切正常。

修法是引入 `sameSource` 判定——不再问「存不存在」，改问「是不是同一个」：

```go
// os.Lstat + os.Stat + os.SameFile
if sameSource(src, dst) {
    return nil          // 真幂等
}
```

不同源？那就得替换。而替换本身，是这一章真正的深渊。

---

## 三 · 备份是唯一的桥

`relinkDir` 的旧实现，逻辑朴素得让人害怕：

```go
os.RemoveAll(dst)          // 先删旧的
err := InstallDir(src, dst) // 再装新的
if err != nil {
    continue                // 静默吞掉
}
```

先拆，再建。中间隔着一个可能失败的操作。

失败的理由不需要多离奇——跨分区硬链接、权限不足、目标被占用，随便哪一个都够。一旦 `InstallDir` 返回错误，那个目录已经不在了。旧的删了，新的没建成。

而 `continue` 让这一切**连一行日志都没有**。

用户看到的是：我明明有那个模型，怎么突然没了。

`app_install.go` 后来复盘这段时说过一句话：「我们在一个可能失败的操作前面，先执行了一个不可撤销的操作。这不叫流程，这叫赌博。」

新流程加了一座桥：

```
os.Rename 备份旧目录  →  InstallDir 重建  →  成功：清理备份
                                          →  失败：回滚恢复 + 写日志
```

`os.Rename` 是关键。它不是删除，是**移开**。同分区内是原子操作，几乎不会失败，而且随时可以移回来。

文件级的处理更彻底——直接不删了。`installer.Install` 内部改为「临时链接 + `os.Rename` 原子替换」：

```go
tmp := dst + ".link-tmp"
os.Link(src, tmp)      // 先在旁边建好
os.Rename(tmp, dst)    // 一步换过去
```

替换失败，原文件毫发无伤。因为它从头到尾就没被动过。

**原子性不是性能优化，是一种承诺：要么你看见旧的，要么你看见新的，你永远不会看见「什么都没有」。**

## 四 · 第三个入口

加固到一半，有人清点安装入口，发现有三个：`Install`、`InstallWithOverlay`、`InstallToGlobal`。

前两个都会校验扩展名。第三个不会。

也就是说，`InstallModelFile` 经由 `InstallToGlobal` 这条路，可以把**任意文件**写进全局 custom 目录。不是漏洞被利用的问题，是这条路径压根没设门。

没人是故意的。它只是后加的，加的时候没人想起前面两个哥哥都戴着头盔。

处置很直白：提取 `isSupportedModelExt`（顺带处理 `.ban` 后缀变体），三个入口全部对齐。

这是安装器这轮加固里最没有技术含量、却最典型的一条缺陷——**不一致**。三个做同一件事的函数，两个有校验，一个没有。它不会在测试里暴露，因为每个函数单独看都能自圆其说。它只在有人把三个并排放在一起时才现形。

而把它们并排放在一起，正是审计存在的全部理由。

## 尾声

`go test ./go/installer/` 最后跑出 16/16 PASS，其中 7 个是这轮新增的：硬链接 `SameFile` 断言、symlink、旧副本原子替换、幂等重装、`InstallDir` 硬链接与类型过滤、`InstallToGlobal` 拒绝非模型扩展名。

`installer` 盯着那 7 个新用例看了很久。

它注意到一件事：这 7 个用例，没有一个是在验证「安装能成功」。它们全都在验证**安装失败或重复时会发生什么**。

它想起自己刚被写出来的时候。那时的测试只有一条：给一个源文件，装一次，检查目标存在。绿的。它当时觉得自己已经被验证过了。

「存在」这个词害了它两次。第一次是 `os.Lstat` 的存在判定，第二次是测试里的存在断言。同一个词，同一种偷懒：**用「有东西」冒充「有正确的东西」。**

ADR-028 的负面清单里还留着一条它没能解决的：链接错误分类仍靠英文错误字符串匹配 `cross-device` / `access`。Go 的系统错误文本目前是英文，能工作。但那是运气，不是设计——**任何依赖人类可读文本做程序判断的地方，都是在赌翻译不会到来。**

它把这条记在了自己的技术债本子上，翻到下一页。

**缝**：不可撤销的操作，必须排在所有可能失败的操作之后。顺序不是风格问题——「先删后建」和「先备份后建」写起来只差一个动词，但一个会丢数据，一个不会。

---

**教训**：存在不等于正确，删除不等于替换，先拆后建是拿数据下注。
