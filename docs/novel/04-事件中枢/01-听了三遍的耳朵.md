# 第 04 区域 · 第 1 章 · 听了三遍的耳朵

> 区域归属：`04-事件中枢`（`frontend/src/bus.js` `frontend/src/core/global-handlers.js` `frontend/src/app-modules.ts`）
> 时间线标签：vol-4
> 对应真实事件/代码改动：ADR-008（事件注册位置与防重复规范）、ADR-027（Web Component 对外契约规范化）、bug-chronicle #19（创意工坊遗留 handler 冲突）

---

## 一 · 说一次，听三次

有人切到创意工坊，又切走，又切回来。

然后编辑模式坏了。点一次开关，状态跳两下；再点，跳三下。像一个被反复叫醒的人，越叫越糊涂。

`bus` 查了自己的订阅表。

同一个事件名下，挂着三个 handler。三个都是同一个函数——同一份代码，同一个闭包结构，只是被注册了三次。

它们全都正常工作。它们全都收到了那一条 `emit`。它们全都执行了。

**一次点击，三次响应。**

`bus` 的契约里从来没写过「同一个 handler 只能注册一次」。它的 `on()` 老老实实往数组里 push，返回一个取消函数，然后就不管了。谁 push 了几次，它不问。

「我是总线，不是门卫。」它说。

这句话对了一半。它确实不是门卫。问题在于——**这栋楼里也没有别人当门卫。**

## 二 · 顶层注册的原罪

问题的源头在这样一段代码：

```js
// app-resource-manager/index.js:25 —— 顶层注册，不防重
bus.on("config:resource-types-changed", function () {
  STORE._config = null;
  document.querySelectorAll("app-resource-manager").forEach(function (el) {
    el._init && el._init();
  });
});
```

它写在模块顶层。模块一被 `import`，这行就执行。

单次加载，没问题。

但前端不是只加载一次的世界。组件会被创建、销毁、再创建。模块可能被多处 import。页面切换可能触发重新初始化。每一次，这行都会再跑一遍，再往订阅表里 push 一个。

而它没有对应的清理。

于是订阅数只增不减。用户在页面之间来回切三趟，handler 就有三份。切十趟，十份。它们不会互相覆盖，它们会**互相叠加**。

创意工坊那个 bug（#19）是这条原理的完整演出：每次 `_initWorkshop()` 都重新绑定事件，同时 `wsEditMode` 这个状态变量被闭包重新初始化。旧 handler 抱着旧闭包继续活着，新 handler 抱着新闭包也活着。它们看着两份不同的 `wsEditMode`，对同一次点击给出两种理解。

这不是「事件触发了两次」那么简单。这是**系统里同时存在两个对当前状态的认知，而且它们都认为自己是对的**。

修法当时是两条：`wsEditMode` 提到 `_initWorkshop` 闭包顶部用 `let` 声明保持持久化；`showSiteView` 每次完全重建 DOM，让旧监听随旧 DOM 一起被 GC 带走。

管用。但那是止血，不是免疫。

## 三 · 两种守卫

ADR-008 把这件事从「修一个 bug」升级成了「立一条法」。

法条分两类，因为项目里有两种订阅场景。

**第一种：模块级、全局、只该有一份。**

用布尔守卫：

```js
if (!_registered) {
  _registered = true;
  Events.On("queue:status", ...);
  Events.On("queue:file-start", ...);
  Events.On("queue:file-done", ...);
}
```

`community/download-queue.js` 早就这么干了。它是当时全项目唯一一个做对的地方，于是被 ADR 抓出来当了正面教材。

**第二种：组件级、随实例生灭。**

用 `_unsubs` 数组 + 生命周期配对：

```js
connectedCallback() {
  this._unsubs.push(bus.on('resource:changed', this._onChange));
}
disconnectedCallback() {
  this._unsubs.forEach(fn => fn());
  this._unsubs = [];
}
```

这一条的关键不在于「记得清理」，而在于**注册与清理必须处在同一个抽象层次**。

`connectedCallback` 里 `on` 的，就得在 `disconnectedCallback` 里 off。不能在别的地方顺手清，不能在某个业务分支里"顺便"取消。因为一旦清理逻辑离开了生命周期钩子，它就依赖某条特定路径被走到——而 UI 里没有哪条路径是一定会被走到的。

`bus` 对这一条特别有感触。它见过太多「在关闭按钮的 handler 里做清理」的写法。那些代码在用户点关闭按钮时完美工作，在用户按 ESC、点遮罩、切路由、或者浏览器直接销毁组件时，全部失效。

**清理不能挂在用户的善意上。**

## 四 · 发射侧也有规矩

ADR-008 管订阅侧。它落地不久，ADR-027 从另一头补上了发射侧。

因为光管住「谁在听」还不够。还得管住「谁在喊、用什么通道喊、喊的内容长什么样」。

Web Component 对外有两条通道：`bus.emit`（跨组件广播）和 `CustomEvent`（沿 DOM 树冒泡）。它们的适用场景不同，但在只想「让另一个组件知道点什么」的时候，用哪个都能跑通。

于是两条通道被混着用。同一类语义的通知，有的走 bus，有的走 DOM 事件。想订阅的人得先猜它走的哪条路。

ADR-027 把选择标准写死，顺带钉死了两条格式：事件名一律 `kebab-case`，payload 一律显式类型约束。

两条 ADR 加起来，事件中枢才算有了完整的宪法——**订阅侧管注册与清理，发射侧管通道与格式。**

`bus` 后来在自己的文档里加了一句注解：

> 我不去重。这是设计，不是缺陷。去重意味着我要判断两个 handler 是否"相同"，而闭包让这个判断在语言层面就是不可靠的。所以我把责任交还给注册方——**你要保证你只注册一次。**

## 尾声

`bus` 有时候会想象自己的订阅表长什么样。

理想状态下，它应该像一个整齐的通讯录：每个事件名下挂着一串明确的收件人，每个收件人都知道自己为什么在这儿，也都知道自己什么时候该走。

现实中它更像一个从没人退过群的群聊。

新人不断加入，老人从不退出。有些成员早就离开了公司——它们所属的组件已经被销毁，DOM 节点已经不在文档里，闭包里的引用指向一片没人访问的内存。但订阅表还攥着它们。它们还会收到消息，还会兢兢业业地执行，去更新一个不存在的界面。

这就是内存泄漏的真面目。不是内存"漏"出去了，是**有人替已经死掉的东西保管着通行证**。

而 `bus` 就是那个保管人。它的引用让那些组件永远无法被回收——**总线的强引用，是前端最温柔的一种谋杀。**

它想不出解法。它只能把规矩写清楚，然后指望每一个来注册的人都记得回来销号。

「事件系统的可靠性，」它在 ADR-008 的边上留了一句，「上限取决于最粗心的那次注册。」

**缝**：注册是显式的，清理是隐式的——这个不对称是所有事件泄漏的温床。语言会强制你写下 `on`，但没有任何机制强制你写下对应的 `off`。

---

**教训**：不防重的注册是复利，注册与清理必须在同一层抽象里成对出现。
