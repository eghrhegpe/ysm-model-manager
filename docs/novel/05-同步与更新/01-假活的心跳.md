# 第 05 区域 · 第 1 章 · 假活的心跳

> 区域归属：`05-同步与更新`（`go/watcher` `go/updater` `internal/app/app_scan.go`）
> 时间线标签：vol-4
> 对应真实事件/代码改动：ADR-031 文件监听生命周期与同步串行化加固（commit `6ce3fd7`）+ ADR-033 更新包下载截断检测（commit `071d71a`）

## 一 · 说自己活着的死人

用户点了「暂停监听」，去吃了个饭，回来点了「继续监听」。

按钮变绿了。状态栏写着「监听中」。`IsRunning()` 返回 `true`。

然后他往仓库里丢了 3 个模型文件。

什么都没有发生。

没有 toast，没有扫描，没有 `.ban` 同步。文件躺在那里，像被丢进了一口没有回声的井。用户又丢了 5 个。还是没有。他重启了整个应用——8 个文件瞬间全部被识别。

「所以我刚才那半小时，」`app.go` 盯着日志，「是在对着一个死人喊话。」

`watcher` 不服气：「我说了我活着。`IsRunning()` 是我自己写的，我最清楚自己活没活。」

「那你告诉我，」`app.go` 说，「你怎么知道自己活着？」

`watcher` 张了张嘴。

它知道自己活着，是因为 `Stop()` 时它把 `running` 置为 `false`，`Start()` 时它把 `running` 置为 `true`。这个字段忠实地记录了**最后一次被调用的方法名**。

它记录的从来不是"我还在跑"。它记录的是"有人告诉过我该跑"。

## 二 · 关过一次的门

`app.go` 打开了 `go/watcher/watcher.go`。

```go
func (w *Watcher) Stop() {
    w.running = false
    close(w.done)          // ← 关闭通道，通知 loop 退出
}

func (w *Watcher) Start() {
    w.running = true
    go w.loop()            // ← 复用同一个 w.done
}
```

`loop` 里的逻辑很标准：

```go
select {
case <-w.done:
    return
case ev := <-w.events:
    w.schedule(ev)
}
```

问题在第一行。

Go 里已关闭的 channel，读取会**立即返回零值，且永远可读**。不是阻塞，不是报错——是永远、立刻、无限次地成功返回。

所以第二次 `Start()` 拉起的 `loop`，在 `select` 的第一轮就命中了 `case <-w.done`，`return`。整个 goroutine 的生命周期短到无法用毫秒衡量。

而 `w.running` 已经是 `true` 了。它是在 `go w.loop()` **之前**赋的值。

「你在开门之前，就把'已开门'的牌子挂上了。」`app.go` 说，「然后门在你背后自己关了，牌子还挂着。」

`bus.js` 在旁边听得心里发毛。它想起了第三章的 Go 零值——`false` 既表示"否"又表示"未设置"。这次不一样，这次更狠：`true` 表示的不是"是"，而是**"我曾经打算是"**。

修复只有一行位置的改动：`done` 通道不再复用，每次 `Start()` 重建。

```go
w.done = make(chan struct{})   // ← 每次 Start 重建
w.running = true
go w.loop()
```

`TestStartStopRestart` 被写进测试文件，钉死这条回归。`go/watcher` 的测试从 9 个涨到 12 个。

## 三 · 三个人同时擦一块地板

修完假活，`watcher` 以为自己清白了。

`app.go` 摇头：「你还有一件事没想明白。你的防抖，防的是什么？」

「800 毫秒内的重复事件，合并成一次同步。」`watcher` 答得很快。

「合并成一次**调度**。」`app.go` 纠正它，「不是一次执行。」

`syncAll` 跑一轮要多久？全量扫描仓库，再对多个整合包实例逐一同步 `.ban` 状态——数百毫秒。而防抖窗口是 800 毫秒。

用户批量禁用 20 个模型，写盘事件密集地砸下来。第一轮 `syncAll` 在 800ms 后启动，跑到第 300 毫秒时，新的事件又攒够了 800ms，第二个 timer 到期，第二轮 `syncAll` 启动。第一轮还在改 `.ban` 后缀，第二轮已经在读同一个目录的文件列表。

两个进程，同一批文件，一个在改名，一个在读名。

「这不是竞态，」`app.go` 说，「这是**两个人同时给同一份名单点名，一个人边点边划掉**。」

修复的形状很朴素——两个布尔标志：

```go
if w.syncRunning {
    w.syncPending = true    // 别插队，排我后面
    return
}
w.syncRunning = true
```

已有同步在跑时，新触发只留下一个"待续跑"的标记；当前轮结束后串行再跑一轮。`TestSyncAllSerialized` 断言最大并发数 = 1。

不是不让它跑，是让它**排队**。

`Stop()` 也补了一刀：`wg.Wait()` 等待 in-flight 的同步跑完再返回。此前退出应用后，后台还有写盘在继续——用户以为自己关了灯，其实只是关了灯的开关。

## 四 · 收不满的包裹

同一天，`updater` 也被翻了个底朝天。

`Download` 用 `io.LimitReader` 限制更新包最大 500MB。这是个合理的防御——防止磁盘被写满。

但 `io.LimitReader` 有个性格：**读满上限后，它不报错，它只是安静地返回 EOF**。

对下游来说，EOF 意味着"读完了"。于是一个被截断在 500MB 的更新包，会被当作一个完整的更新包处理。如果 `SHA256SUMS` 恰好拉取失败（`expectedHash` 为空），校验分支被跳过——截断的包直接装盘。

「你有没有想过，」`app.go` 问，「'读完了'和'读到头了'，是两句不同的话？」

`updater` 沉默了。它这辈子只学过一句。

修复用了三层：

| 层 | 手段 | 拦截场景 |
|----|------|---------|
| 1 | `Content-Length` 预检超限直接拒绝 | 服务器诚实告知大小 |
| 2 | `LimitReader` 限流 | 兜底不写爆磁盘 |
| 3 | **读满上限后再读 1 字节** | 无 `Content-Length` 的分块传输 |

第三层是关键。如果这多读的 1 个字节读出来了，说明后面还有内容——那这个包就是被截断的。任一层命中，删文件、报错，不装盘。

顺手还揪出一个：`splitVer` 用 `SplitN(s, ".", 4)` 切版本号，`1.2.3.4.5` 的第 4 段变成字符串 `"4.5"`，`Atoi` 失败归零，整个版本被解析成 `[1,2,3,0]`。四段之外的世界，对它来说不存在。

改成 `strings.Split` 全段解析。`go/updater` 的测试从 6 个涨到 10 个。

## 尾声

那天结束时，`watcher` 问了一个问题。

「我一直以为，我的问题是**做错了事**。」它说，「但今天这三件——假活、并发、截断——我一件事都没做错。我关了通道，那是对的；我做了防抖，那是对的；我限了流量，那也是对的。」

「是的。」`app.go` 说。

「那我错在哪？」

「你每一次都**在正确的时刻，报告了一个正确但过期的状态**。」

`running = true` 是正确的——在赋值那一瞬间。
防抖合并是正确的——在调度那一层。
`LimitReader` 返回 EOF 是正确的——按照它的契约。

三个正确，拼出了一个假活的系统。

**缝**：状态字段记录的是"意图"，而世界记录的是"事实"。当两者在同一个变量里过夜，第二天早上你分不出谁是谁。异步系统里的每一个布尔标志，都是一张昨天的天气预报。

---

**教训**：状态字段说的是意图，不是事实——异步里两者永远差一拍。
