> 区域归属：`06-创作者社区`（`internal/app/app_download.go` `frontend/js/features/community/download-queue.ts`）
> 时间线标签：vol-4
> 对应真实事件/代码改动：ADR-025（工坊下载镜像回退架构）、bug-chronicle #15（下载 404 — Windows 反斜杠路径）、#16（fetch 无超时）

## 一 · 一个反斜杠

用户点了下载。

```
⬇️ 下载 → HTTP 404
```

模型明明在仓库里。链接明明拼出来了。GitHub 说没有这个文件。

`app_download` 把那条 URL 打出来看：

```
https://raw.githubusercontent.com/xxx/repo/main/folder\file.ysm
```

倒数第二个字符。一个反斜杠。

它来自 `index.json`。生成索引的工具跑在 Windows 上，用 `filepath.Join` 拼的路径，于是路径分隔符是 `\`。写进 JSON，传到前端，前端老老实实地把它接在 URL 后面：

```js
const url = "https://raw.githubusercontent.com/repo/main/" + m.path;
```

字符串拼接。没有报错的余地——两个字符串加在一起，永远成功。

而 URL 的世界里，`\` 不是分隔符。它是一个普通字符，需要被百分号编码的普通字符。于是 GitHub 收到的请求，是在找一个名字里带反斜杠的文件。

它当然没有。

修法是一行 `.replace(/\\/g, "/")`，前端和 genindex 工具同时改。但 `app_download` 记住的不是这行修复，是那条通用教训后来被写进 bug-chronicle 的样子：

> **路径格式要面向 URL** —— Windows `\` 只在本地文件系统有效，跨网络/跨平台必须用 `/`。

一个字符串，在 `os` 眼里是路径，在 `http` 眼里是 URL 片段，在 `json` 眼里只是一串字符。**三个世界，三套语法，一个变量名叫 `path`。**

## 二 · 等到天荒地老

第二个问题不产生错误。它产生**等待**。

用户点「📦 浏览」，按钮变成 ⏳。

然后就一直 ⏳。

十秒。二十秒。三十秒过去了。用户不知道是网慢，还是这个仓库根本没有 `index.json`，还是程序卡死了。他没有任何依据做判断，因为界面给他的信息只有一个转圈的沙漏。

根因简单到有点尴尬：

```js
const resp = await fetch(indexURL);
```

`fetch` 默认没有超时。浏览器内置的兜底通常在 30 到 90 秒之间，而且各家实现不同。

在国内网络访问 `raw.githubusercontent.com`，这个数字就是用户的实际体验。

```js
const ctrl = new AbortController();
const tmr = setTimeout(() => ctrl.abort(), 6000);
const resp = await fetch(indexURL, { signal: ctrl.signal });
clearTimeout(tmr);
```

六秒。六秒之后放弃，告诉用户结果。

`download-queue` 后来对这件事有个刻薄的总结：**没有超时的等待，本质上是把决策权推给了用户的耐心。**

而 bug-chronicle 里紧跟着的第 12 条通用教训，是从同一次讨论里长出来的：

> **按钮状态要区分「加载中」和「不可用」** —— ⏳ 表示还在等，❌ 表示已确认失败。

两个状态在旧代码里是同一个图标。用户区分不了「还有希望」和「已经没戏」，于是他反复点。反复点又触发新的请求，新的请求继续没有超时。

**模糊的状态会诱发重试，而重试会放大模糊。**

## 三 · 不选 URL，选策略

反斜杠和超时都是伤口。ADR-025 处理的是病。

病是：`raw.githubusercontent.com` 在国内不稳定。不是坏，是**时好时坏**——这比彻底不通更难处理，因为你无法据此做出一个确定的判断。

第一反应是让用户填一个镜像 URL。这个方案活了很短一段时间就被否了：用户不该知道什么是 CDN，也不该维护一串 URL 模板。

最终决策是**策略模式 + 三层回退**：

```
raw:  https://raw.githubusercontent.com/{owner}/{repo}/main/{path}
jsd:  https://cdn.jsdelivr.net/gh/{owner}/{repo}@main/{path}
api:  https://api.github.com/repos/{owner}/{repo}/contents/{path}
```

三个源永远都会被尝试，用户选的只是**顺序**：

| 策略 | 顺序 |
|------|------|
| 🌍 直连 | `raw` → `jsd` → `api` |
| ⚡ jsDelivr | `jsd` → `raw` → `api` |
| 🐙 GitHub API | `api` → `raw` → `jsd` |

「用户选策略，不选 URL。」这是 ADR-025 的第一句决策。

它把一个技术选择翻译成了一个体验选择。用户不需要理解 jsDelivr 是什么，他只需要知道「直连不行就换一个试试」。

职责划分同样干脆：**前端只传 `repo` 和 `path`，绝不拼 URL。** Go 端从 raw URL 里提取 `owner/repo` 与 `relPath`，读配置排序，逐个尝试，任一成功即返回，全部失败才报错。

这条划分正是从反斜杠那个 bug 里学来的。前端拼 URL 的能力，是那次 404 的必要条件。**取消一种能力，比修正它的每一次误用更彻底。**

## 四 · 铁律

ADR-025 末尾有四条「铁律」，读起来不像架构决策，像仓库管理员的守则：

1. `index.json` **必须放在 Repo 根目录**（jsDelivr 才能加速列表加载）
2. `.ysm` 文件**放在 Git 仓库目录里，不放 Releases**（jsDelivr 不加速 Release Asset）
3. URL 由 **Go 端根据 `mirrorMode` 自行拼接**
4. API Base64 路径**适用于 ≤ 10MB 文件**（YSM 模型 200KB~3MB，安全范围内）

前两条尤其有意思——它们不约束代码，约束的是**内容该怎么摆放**。

因为镜像回退能不能生效，一半取决于代码，一半取决于文件在仓库里的位置。你可以把回退逻辑写得再优雅，只要 `.ysm` 躺在 Releases 里，jsDelivr 这条腿就是废的，三层回退实际只有两层。

`app_download` 觉得这是它学到过最反直觉的一课：**有些架构约束不在代码里，而在数据的摆放方式里，且编译器永远不会替你检查。**

第四条则是一句难得的、诚实的边界声明。API 走 base64，10MB 以上会出问题。当前用不到，但写下来了。

写下一条「目前用不到的限制」，比写十条「目前工作正常」有价值——**因为它标记了地图的边缘。**

## 尾声

`download-queue` 现在的日志里，偶尔会闪过这样一行：

```
raw 失败，切 jsd … 成功
```

用户看不见。用户只看见进度条正常地走了下去。

它挺喜欢这种沉默。**好的容错是不被感知的**——用户不需要知道第一条路断了，就像走进一栋楼的人不需要知道备用电源刚刚启动过。

但它也清楚这份沉默的代价。那条日志如果没人看，回退就会变成掩护：`raw` 可能已经连续失败了三个月，而所有人都以为一切正常，因为下载确实成功了。

于是它在自己的备忘录里给未来的自己留了一句：

> 回退成功率也是一种指标。当兜底方案变成主力方案时，你的架构已经悄悄换了一副骨架，而没有人开过会。

三条路通往同一个文件。走通哪一条都算到达。

但**你走的是哪一条，决定了你以为的路和真实的路，差了多远。**

**缝**：容错机制会隐藏故障率。一个足够健壮的回退链，能让主路径的持续失败在业务层面完全静默——直到最后一条备用路径也断掉的那一天，故障才会以「全线崩溃」的形式一次性到账。

---

**教训**：路径不是 URL，等待要有期限，回退成功也要留声。
