# 第 07 区域 · 第 1 章 · 差一个后缀的名字

> 区域归属：`07-文件与路径`（`go/fileops` `go/paths` `go/recycle` `internal/app/app_install.go`）
> 时间线标签：vol-4
> 对应真实事件/代码改动：bug-chronicle #20 文件夹操作传相对路径 / #21 ClearCustomDir 的 `.ban` 后缀匹配失败 / #23 游戏运行时 `ERROR_SHARING_VIOLATION`

---

## 一 · 回收了 0 个文件

用户右键点了一个文件夹，选「移入回收站」。

toast 弹了出来，绿色的，很礼貌：

```
回收了 0 个文件
```

绿色。成功的颜色。数字是 0。

`app-tree` 盯着这行字看了很久。它想不明白一件事——如果一个文件都没回收，为什么这是绿色的？

「因为没有抛异常。」`app.go` 在后台说，「Go 那边扫了一个目录，扫出来 0 个条目，返回了 0，没报错。它做完了它被要求做的事。」

「它扫的是哪个目录？」

「`[Almeta_owx]【galgame】`。」

`app-tree` 的手指停住了。

那不是一个目录。那是一个**目录名**。

## 二 · 半个地址

仓库树里的每一个节点，`data-dir` 属性存的都是**相对路径**——相对于仓库根。这是树自己的方言：在树的世界里，一切坐标都以根为原点，说 `[Almeta_owx]【galgame】` 就足以定位。

但 `ScanModelEntries`、`RenameDir`、`CreateDir` 这些 Go 绑定住在另一个世界。在那个世界里，路径必须是绝对的——从盘符开始，一路走到底。

于是前端说「去 `[Almeta_owx]【galgame】`」，Go 拿着这句话，从**进程当前工作目录**出发去找。找不到。返回 0 个条目。不报错——因为"找不到东西"和"那里本来就没东西"，在 `os.ReadDir` 的返回值里长得一模一样。

三个操作全中：`dir:recycle`、`dir:rename`、`dir:mkdir`。

「你们互相之间从来没有对过口径。」`app.go` 说，「树以为自己说的是地址。Go 以为自己收到的是地址。**双方都是对的，只是原点不同。**」

修复朴素得近乎乏味——三处调用在进 Go 之前，先 `LoadAppConfig` 拿 `repoRoot`，拼成绝对路径。

```js
const { repoRoot } = await LoadAppConfig();
const abs = `${repoRoot}/${dir}`;   // 树的方言 → Go 的方言
```

一行翻译。翻译之前，两个世界各自自洽，谁也不知道对面在说另一种语言。

`app-tree` 把这条写进了通用教训第 13 条：**树中的路径永远是相对的**。

## 三 · 差一个后缀

同一周，另一个 0 出现了。

右键整合包 → 清空 → `已清空 0 个文件`。

这次路径是对的。`app-tree` 反复核对了三遍，绝对路径，盘符齐全，目录真实存在，里面躺着 47 个文件。

但 `ClearCustomDir` 说：0。

`app.go` 打开了那段代码：

```go
fileName := filepath.Base(p)
repoFile, ok := repoMap[fileName]   // ← 查仓库映射
if !ok {
    continue                         // ← 查不到就跳过
}
```

它拿 custom 目录里的文件名，去仓库映射表里查对应的源文件。查得到就清，查不到就跳。

custom 目录里的文件叫 `xxx.ysm`。
仓库里的同一个文件，因为被用户禁用了，叫 `xxx.ysm.ban`。

四个字符。一个点，三个字母。

`repoMap` 里没有 `xxx.ysm` 这个 key。47 个文件，凡是被禁用过的，全部查不到，全部 `continue`。

「`.ban` 又来了。」`app-tree` 说这话的时候，语气像在念一个老熟人的名字。

第三章那次，`.ban` 是作为一种**温柔的设计**被引入的——不删除文件，只加后缀，随时可逆。这个设计到今天都是对的。它救过用户好几次误操作。

但它在系统里埋下了一条规则，而这条规则从来没有被写进任何文档：

**这座塔里的每一个文件，都有两个合法的名字。**

而所有做文件名匹配的代码，默认自己面对的是一个名字。

修复一行：

```go
lookupName := strings.TrimSuffix(fileName, ".ban")
```

通用教训第 14 条：**`.ban` 后缀无处不在** —— 任何文件名匹配的地方都要考虑它的存在。

## 四 · 被别人握着的东西

第三个 0 更安静，安静到连 toast 都没有。

用户在游戏里，一边玩，一边在管理器里禁用了一个模型。管理器显示禁用成功。切回游戏，模型还在。再切回管理器，还是显示已禁用。

整合包里那个文件，压根没被加上 `.ban`。

没有报错。没有提示。没有 toast——绿色的都没有。

`app.go` 追到了 `os.Rename` 的返回值。Windows 内核吐回来一个错误码：`ERROR_SHARING_VIOLATION`。

共享违例。翻译成人话：**这个文件现在在别人手里，你不能给它改名。**

YSM 加载模型时会打开文件读进内存。正常情况下这个握持只有一瞬间，读完即放。但如果模型是符号链接，而启动器（PCL / HMCL）又没有以管理员权限运行——YSM 可能解析不了链接目标，文件的句柄就那么一直挂着，不释放。

「所以不是我干不了，」`fileops` 说，「是我**不被允许**干。」

「区别在哪？」`app-tree` 问。

「区别在于，」`fileops` 说，「如果是我干不了，我应该报错。如果是暂时不被允许——我应该**等**。」

修复引入了 `isFileLocked(err)`：检测到共享违例时，跳过这个文件，不报错，等下一次 watcher 触发时再试。

这是一个和解，不是一个胜利。软链接加权限的那种情况，等多久都没用——需要用户退出游戏，把链接模式从符号链接改成硬链接或复制。这条被明明白白写进了文档，因为代码解决不了它。

有些锁不在代码这一侧。

## 尾声

三个 0，来自三个完全不同的地方。

一个是**坐标系不同**（相对 vs 绝对）。
一个是**命名空间不同**（`xxx.ysm` vs `xxx.ysm.ban`）。
一个是**所有权不同**（我的文件 vs 别人正握着的文件）。

但它们在用户屏幕上长得一模一样：一行绿色的字，后面跟着一个 0。

`app-tree` 后来想明白了一件事。这三个 bug 真正的共同点，不是路径，不是后缀，不是锁。

是**「没做成」和「没什么可做」共用了同一个返回值**。

`os.ReadDir` 找不到目录，返回空切片。目录是空的，也返回空切片。
`repoMap` 查不到 key，返回零值。文件确实不需要清理，也是零值。
`os.Rename` 失败被吞掉，计数不增加。文件本来就已经是 `.ban`，计数也不增加。

每一次，系统都诚实地报告了它做成的数量。每一次，它都没有报告它**放弃了多少**。

**缝**：0 是一个双关语——它既是"完成了，只是没什么可做"，也是"什么都没做成"。文件系统的每一个 API 都在用同一个数字讲这两个故事，而调用方永远只听见其中一个。

---

**教训**：区分"没什么可做"和"没做成"——它们长得一样。
