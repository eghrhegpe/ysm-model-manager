# 第 08 区域 · 第 1 章 · 每次都缩小一圈的窗

> 区域归属：`08-配置与状态`（`internal/app/app_config.go` `app.go` shutdown 流程 / `frontend/js/core/page-store`）
> 时间线标签：vol-4
> 对应真实事件/代码改动：bug-chronicle #10（窗口尺寸逐次缩小）、#11（关闭窗口时 panic）、Debug Path Review「JSON 配置读出来全是默认值」、ADR-030（后端持久化与健壮性契约）

## 一 · 一个每天都变矮的房间

第一天，窗口是 1280×800。

第二天启动，小了一点。用户没在意——可能是自己拖过。

第三天，又小了一点。

第四天他确定了：**每次重启，窗口都会缩水一圈。**不是随机的，是稳定的、可预测的、每次缩掉同样一小条的缩水。像一间每晚都会矮掉几厘米的房间。

`app_config` 检查了自己的持久化流程。它存了什么，就读回了什么。字节级一致，没有损坏，没有截断。

它存的是 1256×760。上一次它存的是 1280×800。

**它没有存错。它存的是别人递给它的东西。**

## 二 · 两个都叫「尺寸」的东西

递东西过来的是前端：

```js
window.addEventListener("resize", () => {
  App.SaveWindowPosition(x, y, window.innerWidth, window.innerHeight);
});
```

`window.innerWidth` / `innerHeight`——**内容区**的尺寸。

而 Go 在 shutdown 时拿这两个数去设置**外层窗口**的尺寸。

```
外层窗口 = 内容区 + 标题栏 + 边框
```

于是每一轮：外层设为 1280 → 内容区实际得到 1280 减去边框 → 前端把这个减过的数存回去 → 下次启动外层设为这个减过的数 → 内容区再减一次。

**一个每次迭代都损失一个标题栏高度的递减数列。**

没有任何一步是错的。前端诚实地报告了它能看见的尺寸——它站在内容区里，它看见的就是内容区。Go 诚实地把收到的数字设置给了窗口——它拿到一个宽和一个高，它没理由怀疑。

错的是那个交接口。两边都管它叫「窗口尺寸」，而两边心里想的是两个不同的矩形。

修法极简：**删掉前端的 resize handler。**

不再由前端上报。Go 在 shutdown 时自己调用 runtime 读取真实窗口尺寸（含标题栏与边框）后保存。

问的人变了，问的对象变了，答案就对了。

`app_config` 从这件事里提炼出一条它后来反复引用的话：**当一个值需要跨越抽象边界传递时，单位和坐标系必须跟着值一起过境。** 只传数字，不传语义，等于让对面自己猜。

而对面永远会猜「跟我这边一样」。

## 三 · 死在临终遗言里

窗口的尺寸修好了。然后它开始在关闭时崩溃。

```
panic: runtime error: invalid memory address or nil pointer dereference
```

发生在 `WindowGetSize()` 调用时。偶现，只在某些 Windows 配置上。

这是最难受的一类 panic——**它发生在退出路径上**。

用户点了叉，他已经准备走了。程序在这一刻炸掉，除了留下一个丑陋的错误弹窗和一份没保存成功的配置之外，没有任何意义。它连"及时暴露问题"这个价值都没有，因为它暴露的是一个即将消失的进程的问题。

根因在 Wails runtime：shutdown 流程中某些条件下它返回 nil，而 `WindowGetSize` 没有防御。

修法是给 shutdown 上一层 recover：

```go
func (a *App) shutdown() {
    defer func() {
        if r := recover(); r != nil {
            // 忽略 panic，安全退出
        }
    }()
    // ... 保存窗口状态
}
```

`app.go` 当时对这个 recover 是有抵触的。吞掉 panic 违背它一贯的原则——**错误应当被看见**。

但它最终接受了，理由写在 bug-chronicle 的通用教训第 10 条里：

> **shutdown 必须 recover** —— Wails runtime 关闭时可能 nil panic，必须有防御性 recover。

因为退出路径的语境是特殊的。在这条路径上，「继续正确地运行」已经不是目标了，**「干净地消失」才是**。一个在临终时刻抛出的异常，没有任何下游可以处理它，也没有任何后续操作会被它保护。它唯一的效果是把一次正常退出变成一次崩溃。

**在别的地方，吞掉异常是渎职。在 shutdown 里，它是礼貌。**

## 四 · 读出来全是默认值

还有第三件事，藏在更早的 Debug Path Review 里，只有一行标题：

> Issue: JSON 配置读出来全是默认值

用户改了设置。关掉程序。再打开——全回去了。

这类症状的候选根因有一大把：文件没写成、路径不对、写在了另一个目录、结构体字段没导出（小写字母开头，`encoding/json` 直接跳过）、tag 拼错、读的时候用了值传递而不是指针……

它们的共同特征是：**全部不报错。**

`json.Unmarshal` 遇到不认识的字段，默认行为是忽略。遇到缺失的字段，默认行为是留零值。这两个「默认行为」组合起来，可以让一份完全对不上号的配置文件，安安静静地反序列化成一个全默认的结构体，返回 `err == nil`。

它太宽容了。宽容到无法区分「这个字段用户没设」和「这个字段我压根不认识」。

ADR-030 后来把持久化这一整块收进了一份契约：写要原子（临时文件 + rename）、读要有默认兜底、失败要可见、结构变更要能向后兼容。

其中「失败要可见」这一条，正是从这个 bug 里长出来的。因为最贵的不是配置丢了，是**配置丢了而系统认为一切正常**。

## 尾声

`app_config` 后来给自己画过一张图，图上只有三个词：

```
写入 → 存储 → 读出
```

它一直以为自己的职责是中间那个箭头——把东西存好，别弄丢。

这三个 bug 教它的是：**它真正的职责在两端。**

写入端，它要确认收到的东西是它以为的那个东西（内容区尺寸 ≠ 窗口尺寸）。
读出端，它要确认还原出来的东西还是原来那个东西（全默认值 ≠ 读取成功）。

而中间那段——文件系统、序列化、字节——反而是最不容易出错的部分。磁盘很少骗人。骗人的是**两端对同一个词的不同理解**。

它还想起那个 shutdown 里的 recover。

一个程序最后做的事，是保存自己的状态。这件事做失败了，它不该因此拒绝死去。它应该安静地退出，然后在下一次启动时，用上一次成功保存的状态醒来——**哪怕那份状态旧了一点。**

「旧的状态比崩溃好，」它想，「默认的状态比旧的状态差，但也比崩溃好。」

**顺序是：正确 > 陈旧 > 默认 > 崩溃。**

它把这行写在了自己的注释里。

**缝**：跨层传递的数值必须携带语义。「宽度」不是一个自解释的概念——它需要回答「从哪量到哪」，而这个答案只存在于发送方的脑子里，从不存在于类型系统中。

---

**教训**：内容区不是窗口，读到默认值不等于读取成功，临终时刻应当允许沉默。
