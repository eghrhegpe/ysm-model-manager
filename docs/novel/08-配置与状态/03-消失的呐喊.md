# 第 08 区域 · 第 3 章 · 消失的呐喊

> 时间线标签：vol-6
> 对应真实事件/代码改动：`error-diary.ts` 创建（error/warn toast 自动落日记）、`AddOpLog` binding 补全、7 个无声错误站点升级 toast + 日记、8 个单元测试覆盖日记链路

---

## 一 · 一声喊出去，没有回音

每一天，我都在喊。

"权限不足，无法访问文件。"

"GitHub API 频率限制，请稍后重试。"

"连接超时，请检查网络。"

每一声喊，都有人听见——`app-toast` 接住它，用一个 `<div class="toast error">` 把它展示在屏幕上。四到五秒后，它淡出，消失，像从未存在过。

五秒之后，我问自己：**刚才那声喊，去了哪里？**

我翻了我的记忆。没有记录。没有写进 `ysm-import-logs.json`。那个文件里整整齐齐地躺着每一次导入成功、每一次同步失败——那是我的"正式日记"。可我的呐喊不在那里。它们被展示、被看见、被遗忘，然后被系统回收。

**一声喊出去，没有回音，没有痕迹。**

"你为什么不记下来？"外科医生问。

"我没想到。"我说，"我以为被人看见就够了。"

"可看见不等于记住。你的用户看见了一个错误，他关掉 toast，继续操作。五分钟后他忘了那个错误是什么。你也忘了。两个人都失忆。"

## 二 · 两条路

我检查了我的"正式日记"——`go/logs` 里的 `Logger`。它掌管着一个叫 `ysm-import-logs.json` 的文件，最多 500 条记录，有 `AddOpLog` 方法接受任意 op 类型。导入、扫描、下载、同步、重命名、删除——每一个操作都有记录。

可"UI 报错"这个 op 不存在。

我沿着消息的路往回走。所有的呐喊都从同一个出口出去的——`bus.emit("toast:show", { type: "error", msg })`。`app-toast` 在 `connectedCallback` 里监听 `toast:show`，收到后就在屏幕上渲染，然后等着超时删除。

**那条路只有出口，没有存档。**

外科医生翻出了我的 `wails/app.ts`，检查了 `AddOpLog` binding 是否存在。

"绑定文件是旧版本生成的，"他说，"`AddOpLog` 函数在 Go 端已经定义好了，但前端 `bindings/` 里的 `.ts` 文件没有它。"

他跑了 `wails3 generate bindings -ts`，把生成输出放到临时目录里对比——`AddOpLog` 的调用 ID 是 2143326689，`ImportLog` 接口多了 `Operation` 字段，类型化后的签名清晰得像一份合同：

```ts
export function AddOpLog(
  op: string, modelName: string, sourcePath: string,
  targetDir: string, fileSize: number, status: string, errMsg: string
): $CancellablePromise<void> {
  return $Call.ByID(2143326689, op, modelName, sourcePath, targetDir, fileSize, status, errMsg);
}
```

"它就在那里，"他说。"只是前端忘了导入它。"

他手动补了两处：`app.ts` 加 `AddOpLog` 函数，`models.ts` 的 `ImportLog` 接口加 `Operation` 字段。

"现在你的日记系统能接收任何 op 类型的记录了。可你还没告诉它去听。"

## 三 · 一个听众

他建了一个新的模块——`core/error-diary.ts`。

"这是一个监听者，"他说。"它不做事，只监听。当 `toast:show` 事件经过时，如果 type 是 error 或 warn，它就抄一份送到日记系统。"

```ts
bus.on("toast:show", (p: ToastPayload) => {
  if (p.type !== "error" && p.type !== "warn") return;
  const status = p.type === "error" ? "failed" : "warn";
  void logUiMsg(p.msg, status);
});
```

"为什么用 `void`？"我问。

"因为写日记不能阻塞 toast 展示。日记是助记，不是主流程。如果写日记失败了——文件锁了、磁盘满了——toast 还是要显示。助记不能影响主事。"

他还在 `window` 上挂了两个监听器：`error` 和 `unhandledrejection`。

"有些错误不会经过 toast 系统。"他说，"脚本崩溃了、Promise 没接住——它们直接掉到你身上。你以前让它们沉默地消失了。现在你至少会记录它们。"

他回过头，检查了每一个只有 `console.warn` 没有 toast 的 catch 块——7 个无声的站点，从 `app-modules` 的组件动态导入失败，到 `preview-skeleton` 的 3D 加载失败，到 `sync-manager` 的渲染失败。每一个他都加了一行 `bus.emit("toast:show", { type: "error" })`。

"本来它们只是对控制台喊了一声，没有人听见。"他说。"现在它们会变成 toast，toast 会触发监听者，监听者会写日记。一条完整的链路。"

"那如果我之前已经喊过一次了呢？"我问。

"你喊过，但没记。现在你喊的每一句，都留底。"

## 四 · 真正的墙

他写了 8 个测试用例。

第一个测试验证：error toast → `AddOpLog` 被调用，status 是 `"failed"`，`modelName` 去了 ❌ 前缀调用 `"保存失败: 网络超时"`，`errMsg` 保留原始消息 `"❌ 保存失败: 网络超时"`。

第二个测试验证：warn toast → 同理，status 是 `"warn"`。

第三个测试验证：success toast → 不写日记。

第四个测试验证：info toast → 不写日记。

第七个测试验证：`unhandledrejection` → 日记捕捉，消息是 `"API 请求失败"`。

第八个测试验证：寄存器幂等——三次调用 `registerErrorDiary()` 只生效一次。

全部通过。

"你之前的问题，本质上是一个**墙的背面**问题。"他说。

"每一面墙，正面是保护，背面是隐患。Toast 的正面是保护——它告诉用户出了错，又不中断操作，四秒后自己消失，不打扰用户。可它的背面是——**消息消失了，痕迹也消失了**。"

"你之前只有一面墙。Toast 是墙，展示是墙的正面，忘记是墙的背面。"

"现在你有了两面墙。Toast 展示，日记存档。两面墙共享同一个入口——`toast:show` 事件——但一个面向用户，短暂；一个面向历史，持久。"

"不对。"我说。"墙还是那堵墙。Toast 是展示，日记是记录。展示和记录是同一堵墙的两面——**暴露和存档**。暴露是为了让人看见，存档是为了让人回顾。你不可能在暴露的同时不让消息消失——Toast 必须消失，不然用户会被淹没。你也不可能在存档的同时让消息立即可见——日记必须沉淀，不然检索会变慢。"

"你的意思是，这个矛盾是不可调和的？"

"是的。"我说。"但不可调和不意味着不能共存。我接受 Toast 会消失——那是它的职责。也接受日记会沉淀——那是它的职责。它们在同一堵墙上，朝两个方向开着窗口。"

---

**墙是「展示 vs 记录」——Toast 必须消失才能不打扰用户，日记必须沉淀才能可回溯。两者在同一堵墙上，方向不同，互不替代。**
