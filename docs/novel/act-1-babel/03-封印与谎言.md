# 第三章 · 封印与谎言

**第一幕 · 巴别塔 | 对应真实事件**：v1.0.5–v1.0.9，`.ban` 后缀匹配失败 + BOM 毒药 + Go bool 三态 + `ClearCustomDir` 清空 0 个文件

---

如果说第一章的裂缝是"同一条消息，两种解读"，第二章的裂缝是"同名的代码，两个版本"，那这一章的裂缝是更微妙的东西——

**同一个标记，三种意思。**

---

## 一 · 封印

YSM 世界里，每一个模型文件都有自己的命运。

健康的模型以 `.ysm`、`.zip`、`.7z` 的后缀活在仓库中。但一旦被禁用，它们就会被加上 `.ban` 后缀——像一道封印，锁住了模型的力量。

```
[碎de帆]【东方Project】博丽灵梦2025-08.ysm     （绿色，活跃）
                                                    ↓ 点击禁用
[碎de帆]【东方Project】博丽灵梦2025-08.ysm.ban   （灰色，被封印）
```

这个机制本是一个优雅的设计——不删除文件，不改内容，只是改个名字。禁用就是加后缀，启用就是去后缀。可逆、安全、不丢数据。

但任何优雅的设计，在复杂的现实面前都会变得狼狈。

`ClearCustomDir` 是负责清空整合包的函数。它扫描整合包的 `custom` 目录，找到每一个文件，然后去仓库的映射表里查——这个文件对应仓库里的哪个模型？查到了就删，查不到就跳过。

一天，用户右键整合包 → 清空 → 看到了一行字：

**"已清空 0 个文件。"**

仓库中有个文件叫 `haku.ysm.ban`（已禁用）。整合包的 `custom` 目录中有个文件叫 `haku.ysm`（已安装）。当 `ClearCustomDir` 用 `filepath.Base(p)` 提取文件名 `haku.ysm` 去查仓库映射时——

仓库映射的键是 `haku.ysm.ban`。

`haku.ysm` ≠ `haku.ysm.ban`。

匹配不上。0 个文件被清空。

"已清空 0 个文件，"`ClearCustomDir` 至今记得它说出这句话时的茫然。它明明扫描了 20 个文件，却一个也没清掉。

事后复盘，一个满头白发的 Go 函数对它说："你忘了 `strings.TrimSuffix(name, ".ban")`。任何文件名匹配的代码，都必须先去后缀再匹配。这是铁律。"

`.ban` 封印是一个保护——它让禁用变得可逆。但保护本身也成了障眼法：你以为你在匹配名字，但名字上贴着一层你看不见的封条。

## 二 · BOM

还有一个更古老的诅咒——BOM。

UTF-8 编码规范中一个幽灵般的存在：文件开头的三个字节 `EF BB BF`。在大多数编辑器中看不见，摸不着。

但 Go 的 `json.Unmarshal` 看到了它们。

不是"看到了"——是"被它们毒死了"。

PowerShell 写入的 JSON 配置文件，总是带着这个 BOM 头。`json.Unmarshal` 读到这三个字节，不会报错——它会**静默解析失败**，返回零值。

于是配置回退为默认值。

于是一遍又一遍地重设路径。

于是有人对着屏幕咆哮："我明明保存了！"

BOM 是一个保护——它让编辑器知道文件的编码是 UTF-8。但保护本身也成了毒药：你以为你的配置被保存了，但保存的时候附带了一个 Go 不认识的前缀，于是保存等于没保存。

**保存了，但没完全保存。** 这就是 BOM 的谎言。

"所有 JSON 读取必须用 `readJSONFile()`，里面加 `bytes.TrimPrefix` 去 BOM。"这是写在世界法则里的又一条铁律。

## 三 · 三态

同一天，另一个谎言在 Go 的类型系统里被揭穿。

YSM 文件头里有一个 `free` 标签——标记这个模型是否免费。Go 端的 struct 把它映射成了 `HasFree bool`。

Go 的 `bool` 默认值是 `false`。

这意味着：**没有读到 `free` 标签时，`HasFree` 也是 `false`。**

而前端的逻辑是：`hasFree === false` → 显示 🔒（付费模型）。

于是所有没有声明 `free` 标签的模型——不管它是不是免费的——都被标记为付费。

这不是 Bug。这是类型系统给你开的一个玩笑。布尔变量只有两个值，但现实世界有三种状态——是、否、**未说明**。

`false` 可以表示"不免费"，也可以表示"没读到"。

你分不清。

三态问题在计算机科学中是最古老的笑话之一。null、undefined、0、false——每种语言都有自己的三态地雷。Go 用零值制造了它的地雷，JavaScript 用 `undefined` 制造了它的，SQL 用 `NULL` 制造了它的。

它们是同一颗炸弹的不同引信。

修复方案：`HasFree` 只在明确读到 `free` 标签时才设为 `true`。没读到就不设置。前端的三态逻辑：`hasFree === undefined` → 不显示标记，`hasFree === true` → 🆓，`hasFree === false` → 🔒。

三个状态，三种呈现。不再有歧义。

## 四

那天晚上，`app.go` 把三个事件排成一排，看了很久。

`.ban` 封印：保护了可逆禁用，但让文件名匹配多了一个隐藏后缀。
BOM：保护了编码识别，但让 JSON 解析静默失败。
Go bool：保护了类型安全，但让"否"和"未知"变成了同一个值。

三个保护。三个暗缝。三种"你以为它做了 A，其实它还做了 B"的谎言。

它开始理解一件事：**每堵墙都有两面。** 朝外的那面写着"保护"，朝里的那面写着"裂缝"。你筑墙的时候只看了外面，但裂缝在里面。

而裂缝不会自己说话。它只是静静地等着，直到某一天——用户按下按钮，什么都没发生，或者 0 个文件被清空，或者配置丢失了——那时候你才发现，墙里面一直有个洞。

`app.go` 在日志里写下了一行字：

**"UI 会骗人，数据不会。但数据也会被它的格式骗。"**

窗外天快亮了。灵梦的 `.ysm` 安静地躺在仓库里，`haku.ysm.ban` 沉默地站在一旁。

它们不知道什么封印、什么 BOM、什么三态。

它们只知道，当 `ExtractYsmSummary` 解析它们的元数据后，经过 `cleanTips()` 清洗的温馨提示会在预览面板中温柔地浮现。

没有 `§3` 格式码的污染。没有 `\n` 被吞噬的烦恼。

只有干净的信息。

但干净的信息，也需要干净的管道来传输。而管道——从 Go 的结构体到 JSON 的字符串到 JS 的变量——每一段都可能被某个"保护"悄悄污染。

---

**缝**：每种"保护"（`.ban` 后缀、BOM 头、Go 零值）都在数据上叠加了一层隐含意义。数据本身不会说谎，但数据的格式会——因为格式的默认值和"未设置"长一模一样。

**教训**：UI 会骗人，数据也会被格式骗。
