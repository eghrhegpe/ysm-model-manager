# 第五章 · 沙箱诅咒

**第二幕 · 筑墙者 | 对应真实事件**：v1.0.8–v1.0.9，WASM 集成 YSMParser 全过程——8 轮 Debug，根因是 Go `[]byte` 经 JSON 序列化返回 base64 字符串

---

第一幕结束时，YSM 模型管理器看见了巴别塔的裂缝——语言之间、版本之间、格式之间、记忆之间。它以为最坏的情况不过如此。

它错了。

最坏的裂缝不在墙与墙之间。它在墙**里面**。

---

## 一 · 愿望

"我们能不能不跑那个 exe 了？"

`app-preview` 看着 `build/bin/` 目录里的 `YSMParser.exe`，越看越不顺眼。一个桌面应用，要调用外部 exe 来解码模型——这感觉就像开着跑车却要下来推。

"我要 WASM。"

把 C++ 解析器编译成 WebAssembly，嵌入前端，在浏览器里直接运行。没有外部进程，没有临时文件，没有命令行黑框。WASM 是沙箱——安全的、跨平台的、轻量的沙箱。

沙箱是另一种墙。但这一堵墙，所有人都以为它是完美的。

第一步是下载官方发布的 WASM 包。`YSMParser.wasm` 只有 1.1 MB，`YSMParser.js` 胶水代码 75 KB。放进 `frontend/public/wasm/`，加一行 `script src`。

构建。运行。

`WASM init: ❌`

"工厂函数名叫 `YSMParserModule`，不是 `YSMParser`！"

改。构建。运行。

`WASM init: ❌`

"胶水脚本的 `fetch()` 在 Wails 自定义协议下会静默死掉！"——WebView2 的陷阱。本地文件协议下，`fetch()` 返回的 Promise 既不 resolve 也不 reject，就那么挂在那里，像冬天的晾衣绳上的冰凌。

解决方案是把 WASM 二进制直接嵌入 JS。base64 编码，用一个字符串背在肩上。1.5 MB 的 JS 文件来了。

构建。运行。

`WASM init: ✅` — 但输出文件数为 0。

`Unsupported file version detected。`

原来官方发布的 WASM 包不支持这个 .ysm 文件的格式版本。但 CLI 版支持。

"那就自己编译 WASM。"

---

## 二 · 远征

源码就在那里——C++ 写的，用 CMake 构建，支持全版本格式。但要编译成 WASM，需要三件神器：Emscripten SDK、CMake、Ninja。

装。配。编。

`YSMParser.wasm` — 1,135,526 字节。

替换前端文件，重新构建，刷新浏览器。

`WASM init: ✅` — 输出文件数 0。

`Unsupported file version detected。`

同样的源码，同样的版本号，CLI 能解，WASM 不能。

这是沙箱的第一道诅咒：**同一份灵魂，换了一副身体，就认不出自己了。**

---

## 三 · 八轮

App 精灵——`app-preview` 的化身——开始了长达六个小时的排查。

**第一轮：怀疑编译参数。**

Emscripten 的 `-sSHRINK_LEVEL` 是不是把代码路径裁掉了？zstd 库没链接上？AES 加密在 WASM 下有兼容性问题？

"肯定不是编译参数的问题，"AI 助手的声音从头顶传来，带着让人恼火的笃定，"你怀疑的方向错了。"

"那你说是什么？"

"数据。数据根本没进到 WASM 内存里。"

**第二轮：绕过文件 I/O。**

新增 `ysm_decode_from_memory` 桥接函数——直接在内存里创建解析器，`YSMParserFactory::Create(const char* data, size_t size)`。吃进去的是字节，吐出来的是模型，不经过文件系统。

但仍然报 `Unsupported file version`——因为数据根本没写进 WASM 内存。

**第三轮：HEAPU8 不可访问。**

新版的 Emscripten 把所有内存视图藏在了闭包里。`wasmModule.HEAPU8` 是 `undefined`。`wasmModule.asm?.memory` 也不存在。

修复：胶水代码注入 `Module["HEAPU8"]=HEAPU8`。

**第四轮：`const` 重赋值。**

`glueCode = glueCode.replace(...)` 报 `Assignment to constant variable`。

修复：`const` → `let`。

**第五轮：`.replace()` 误改函数定义。**

`"updateMemoryViews()"` 同时匹配了函数定义 `function updateMemoryViews(){` 和函数调用，导致 `function updateMemoryViews();Module["HEAPU8"]=HEAPU8{` 语法错误。

修复：改用 `";updateMemoryViews()"` 带分号前缀。

**第六轮：ALLOW_MEMORY_GROWTH 后 HEAPU8 分离。**

`_malloc(284916)` 触发 WASM 内存扩容。扩容前，`HEAPU8` 指向 16MB 的旧 `ArrayBuffer`。扩容后，WASM 获得了更大的内存块，但 `HEAPU8` 仍然指向已经分离的旧 buffer。

`heap.set(data, ptr)` 写入了旧 buffer——一个已经不属于 WASM 的内存区域。WASM 代码去读新 buffer 的同一个地址，当然全是零。

修复：`_malloc` 之后重新 `_getHeap()` 获取最新引用。

```
[_writeHeap] verify=ef bb bf 59 53 47 50 0d 0a 0d 0a 2d 2d 2d 2d 2d
```

数据写对了。但 WASM 侧仍然报 `Unsupported file version`。

**第七轮：`new Uint8Array(string)` 在 WebView2 返回空。**

`Array.from(src.slice(0,8))` 返回空数组。

修复：改用 `Uint8Array.from(data, c => c.charCodeAt(0))`。

JS 侧的诊断输出：
```
[JS bytes[0-15]]: ef bb bf 59 53 47 50 0d 0a 0d 0a 2d 2d 2d 2d 2d
```

`ef` 没问题。但 App 精灵注意到一个细节——WASM 侧收到的第一个字节是 `37`，十六进制的 `0x25`，ASCII 码的 `%`。

"为什么是 `%`？"她嘀咕着，"文件头的第一个字节应该是 `0xEF` 才对。"

她加了一行：

```js
console.log(typeof bytes, bytes.constructor.name, bytes.length);
```

输出：

```
String 284916
```

*字符串？*

## 四 · 暗渡陈仓

第八轮。

"`ReadFileBytes` 返回了一个字符串。"

App 精灵盯着屏幕，所有的线索在这一刻串联了起来。

Wails 把 Go 的 `[]byte` 通过 JSON 序列化——JSON 规范说，二进制数据要编码成 base64 字符串。于是：

```
Go []byte → JSON base64 编码 → JS 收到 base64 字符串
```

JS 侧的诊断代码用 `atob(bytes)` 解码了 base64 字符串，才得到了 `ef bb bf` 的正确数据。但她写入 WASM 内存时，**用的是未解码的原始 base64 字符串**。

WASM 解析器看到的是 `%7u/WVNHUA0K...`——base64 编码后的文本，不是二进制数据。当然认不出 YSGP 头。

"所以我这半天一直在往 WASM 里写 base64 字符？"她哭笑不得。

五层边界。每一层都可能静默改变数据的类型：

```
[]byte(Go) → base64 string(JSON) → string(JS) → Uint8Array → heap.set() → WASM HEAPU8 → C++ ifstream
```

第一层变了——`[]byte` 变成了 base64 字符串。但她在 JS 侧用 `atob()` 解了码，下意识以为数据已经是二进制了，没去检查变量的 `typeof`。

如果一开始就加一行 `console.log(typeof bytes)`——八轮 Debug 直接变一轮。

她改写了数据接入逻辑：

```js
let bytes = await ReadFileBytes(modelPath);
if (typeof bytes === "string") {
    const binaryStr = atob(bytes);
    bytes = Uint8Array.from(binaryStr, c => c.charCodeAt(0));
}
```

重新编译。重新注入。启动应用。

```
[_writeHeap] src[0]=ef
[WASM-Diag] utf8Header==0xbfbbef? YES
[WASM-Diag] magic3==0x50475359? YES
[WASM-Bridge] Create OK, version=3
[WASM-Bridge] Parse OK
[EXPORT] /output/textures/Eanes.png
[EXPORT] /output/models/main.json
```

整整一百八十七根骨骼。八百七十七个立方体。

"We did it。"App 精灵轻声说。

## 五 · 代价

破解了 WASM 的诅咒后，剩下的工作像多米诺骨牌一样顺滑倒塌。exe 从发版包里被拿掉。模型的骨骼图上出现了 `🧠 WASM` 标签。v1.0.9 发布。

但 App 精灵坐在空荡荡的房间里，盯着控制台上已经安静的日志，问了 AI 一个问题：

"我们绕了八轮 Debug——闭包变量、const 重赋值、字符串替换歧义、内存扩容分离、Uint8Array 构造函数、base64——结果最后的根因是最简单的那一个：JSON 序列化把二进制转成了 base64。"

"所以真正的问题是……"她缓缓说道，"我花了几个小时怀疑 WASM 编译器、怀疑 Emscripten 版本、怀疑 C++ 代码——从来没有怀疑过 Go 端返回的数据类型。"

"因为你觉得 Go 的 `[]byte` 很可靠，"AI 助手接话。

"因为我在 JS 侧用 `atob` 解了码，下意识以为数据已经是二进制了，没去检查变量的 `typeof`。"

**如果一开始就检查 `typeof`——八轮变一轮。**

但她也知道：八轮不是白费的。每一轮都堵住了一个潜在的数据传递漏洞——HEAPU8 的闭包问题、内存扩容的分离问题、字符串替换的歧义问题。这些问题即使不在这次爆发，也会在未来的某一天、某个更大的文件上露出獠牙。

沙箱是安全的。沙箱是跨平台的。沙箱是轻量的。

但沙箱**也是一面墙**——和 Shadow DOM、和 ESM 模块化、和 Go 的零值一样，它保护了安全，也隔绝了真相。在沙箱外面，Go 的 `[]byte` 是字节；在沙箱的入口处，JSON 把字节变成了字符串；在沙箱里面，C++ 期待的是字节。

**墙的两边，数据长不一样。**

而没有人告诉你墙的入口处发生了什么变形。你只能自己走过去，一步一步地，从 Go 到 JSON 到 JS 到 WASM 到 C++，在每一层边界上加一行 `console.log(typeof data)`，直到找到那个被悄悄改变了的东西。

这就是沙箱的诅咒：它保护了你，但你无法看见保护的过程。而看不见的过程，就是最危险的过程。

---

**缝**：五层边界（Go→JSON→JS→HEAPU8→C++），每一层都可能静默改变数据的类型。JSON 序列化是规范不是 Bug，但它在你不知道的地方把 `[]byte` 变成了 base64——保护了传输安全，牺牲了类型保真。

**教训**：跨语言每层验证 `typeof`，不信任任何隐式转换。
