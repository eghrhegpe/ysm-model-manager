# 第八章 · 秘钥之战

**第二幕 · 筑墙者 | 对应真实事件**：v1.4.6，V3 加密格式 WASM 解码 + `callMain` MEMFS 路径复活 + `HideWindow` 防 CLI 弹窗

---

第二幕的前三章讲了三种墙：WASM 沙箱、Shadow DOM、通用化统一。每一堵墙都在保护的同时创造了裂缝。

但这一章要讲的，不是一堵新墙。是一堵**你以为已经坍塌的旧墙，其实从未倒下**。

这是整个故事里最大的反转。

---

## 一 · 双生

事情从一个模型说起。

**「[墓野奈奈]【东方project】芙兰朵露Flandre2025-06.ysm」**

910KB，加密模型。用户双击它，预览面板亮起，控制台开始输出日志：

```
[YSM] WASM init: ✅
[YSM] ✅ 原始字节解码成功: 5 文件
[YSM] ⚠️ WASM 解码成功但几何体解析为空，回退 Go CLI
```

WASM 解码了 5 个文件出来，但几何体解析失败了。5 个文件全是根目录文件——没有 `models/` 前缀。而过滤条件写了 `if (!f.path.startsWith("models/"))`，把 V1 格式的 JSON 全跳过了。

修起来很简单——把 `startsWith("models/")` 去掉。改完构建。

但另一个模型来了。

```
[YSM] WASM detectYsmVersion: 3 (0=未知, 1=V1, 2=V2, 3=V3)
[YSM] ❌ WASM 解码失败，无输出文件
```

V3。一个我们听说过但从未直面过的版本号。

V2 的魔数是 `YSGP`（4 字节），V3 的魔数是 `YSM`（3 字节）。除了魔数，加密算法、数据布局、文件结构可能全都不同。第五章打通的 WASM 路径——`decodeYsmFileFromMemory`——走的是 V2 的重建方案，对 V3 完全无效。

---

## 二 · 偏移

调试员开始了三天的猜谜游戏。

**第一猜：版本号。** 加 `forceVer` 参数，V2 不行就试 V3 header。结果：❌ 失败。

**第二猜：偏移。** 打日志看二进制段头 64 字节，和 `hash` 标签值对比：

```
hash=0b6371ff850f3b739a5b6e94f28a9d3d
dataStart+0:   00 03 00 00 00 7a d5 bc c0 3c da 06 d0 b2 9c 67  ← 不匹配
dataStart+16:  07 ae 58 d4 b1 f4 8c a0 2e 18 dd c7 5b ff 28 c7  ← 不匹配
dataStart+32:  2a f3 fc 57 bc a8 ba 31 dd b5 53 a8 d9 c4 63 3e  ← 不匹配
```

三个 16 字节块，没有一个匹配。V3 文本头部变体的二进制段里**根本没有独立存储的 16 字节 hash**。hash 只在 `hash` 文本标签里。

修复：V3 时 `encryptedStart = dataStart`（不 skip 16），V2 时 `encryptedStart = dataStart + 16`。

结果：❌ 依然是 0 文件。

**第三猜：格式完全不同。** V3 就是 V3。它不是 V2 换了版本号。文本头部剥离方案从根上不适用于 V3。

但等等——postmortem 里写着：WASM 明明解过 V3！Eanes 模型——187 骨 877 方的加密 .ysm——就是在 WASM 路径下成功的。

同一个 WASM 二进制，能解 Eanes，不能解芙兰朵露？

问题不在 WASM 能不能解 V3。问题是**我们的重建格式不对**。

---

## 三 · 死者复苏

调试员重新翻开了 `ysm-parser.js`。这个文件里有两个导出函数：

```js
export async function decodeYsmFileFromMemory(bytes) { ... }  // 内存解析
export async function decodeYsmFile(bytes) { ... }             // MEMFS + callMain
```

`decodeYsmFileFromMemory` 走的是 C++ 工厂方法，直接吃字节数组。它不处理文件 I/O，不识别文本头部。

`decodeYsmFile` 走的是 `callMain`——把文件写入 Emscripten 的虚拟文件系统（MEMFS），然后调用 YSMParser 的 CLI main 函数。它走的路径和 CLI exe 完全一样——能从文件系统读取、能识别文本头部。

但 `decodeYsmFile` **被弃用了**。

故事要回到第五章。那时候 `callMain` 总返回 "Unsupported file version detected"。排查了八轮，最终根因是 base64 编解码——`ReadFileBytes` 返回 base64 字符串，代码直接当二进制喂给了 WASM。

从那以后，代码就走 `decodeYsmFileFromMemory` 了，`callMain` 路径被标注为"必然失败"。

**但 base64 的 Bug 早就在 v1.0.9 时修复了。** 当前的解码流程第一步就是 `atob()` → `Uint8Array`。`callMain` 的数据链路现在已经干净了。之前卡它的原因已不复存在。

被标注为"必然失败"的路径，在三个月后被证实——**它从来就没失败过**。它只是需要一个正确解码的 base64。

调试员决定复活它。

第一次运行——JS 报错了。

`Cannot access 'files' before initialization`

又是 TDZ。`let files;` 被声明在 V3 块之后，V3 块里 `files = await decodeYsmFile(bytes)` 时 `files` 还在 Temporal Dead Zone 里。

修完之后，构建。测试。控制台亮起了一行等了三个小时的日志：

```
[YSM] V3 文件，尝试 MEMFS 文件路径解码...
[YSM] ✅ V3 MEMFS 解码成功: 42 文件
```

42 个文件。1200 根骨骼。4714 个立方体。一个 4.7 MB 的加密 V3 模型，通过 WASM 的 callMain 路径，全部解码成功。

**死去的代码突然复活了。**

---

## 四 · 无窗之境

V3 的 WASM 路径打通了。但 V3 在 WASM 失败后，会回退到 Go 的 `runYSMParserOnFile`。这个函数调用 `exec.Command`——Windows 上默认会弹一个 CMD 黑框。

`cmd.SysProcAttr = &syscall.SysProcAttr{HideWindow: true}`——两行代码。CLI exe 从此在后台静默运行。

完整的解码链路终于被打通了：

```
.ysm 文件
  │
  ├─ detectYsmVersion
  │    ├─ =3 → decodeYsmFile(MEMFS) → 成功
  │    │                         └─ 失败 → Go CLI (HideWindow)
  │    ├─ =2 → decodeYsmFileFromMemory → 成功
  │    │                         └─ 失败 → strip header → 重建 → decodeYsmFileFromMemory
  │    └─ =0 → 同上 V2 流程
  │
  └─ 全部失败 → Go CLI (HideWindow)
```

三条独立的解码路径，从最快到最慢，从最轻到最重。前两条无窗口，最后一条也隐形了。

---

## 五

`app.go` 看着流程图，没有感到圆满。

它想起了第五章的八轮 Debug。那时候，`callMain` 被判了死刑——"必然失败"。所有人都信了。bug-chronicle 里写着它失败。AGENTS.md 告诉新 AI 它失败。三个月里，没有任何人重新评估过这条路径。

但真相是：**它从未失败。**

失败的不是 `callMain`，失败的是它上游的数据链路——base64 编解码。当上游修好了，`callMain` 就能工作了。但没人回头看。

"废弃"不是永久的。它是暂时的——标注了一个"当前不可用"的状态。但"当前不可用"和"永远不可用"不是同一件事。

**这又是一种边界**——"废弃"和"死亡"之间的边界。废弃的代码还在仓库里，它的逻辑还在，它的功能还在。只是没人调用它了。而当你需要它的时候，它会安静地等着你，像一扇被锁了三年的门——锁是别人加的，但钥匙一直就在锁孔里。

`app.go` 在日志里写道：

**"没有真正'废弃'的代码路径——只有暂时不可用的代码路径。Bug 修复后，废弃标签应该重新评估。"**

第二幕结束了。

YSM 模型管理器筑了三堵新墙——WASM 沙箱、Shadow DOM、通用化统一——每堵都开了裂缝。它还发现了一堵旧墙从未真正倒下——`callMain` 的路径从未失败，只是被错误地标注了。

它开始怀疑：是不是每堵墙都在制造问题？但如果拆墙，会回到旧帝国的全局污染。

这个两难——筑墙有缝、拆墙有灾——将在第三幕得到解答。不是通过消灭裂缝，而是通过另一种方式。

---

**缝**：被标注为"必然失败"的代码路径从未真正失败——是上游的 base64 Bug 让它看起来坏了。Bug 修复后，废弃标签没有重新评估，死去的代码被埋了三个月。

**教训**：废弃≠死亡，修复上游后必须重新评估下游。
