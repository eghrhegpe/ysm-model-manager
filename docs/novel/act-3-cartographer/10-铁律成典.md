## 一 · 编年

`bug-chronicle.md` 已经很厚了。

从第 1 条"文件夹开关只读不写"到第 38 条"renderDisplayName 着色顺序反转"，每一条都记录了症状、根因、修复和教训。有些简单——一个符号写反了。有些复杂——5 层边界的数据类型链路，8 轮 Debug 才找到根因。

但 `app.go` 发现了一个问题：**Bug 记录是按时间排列的，不是按类型排列的。**

你翻开 `bug-chronicle.md`，看到的是一条一条的事件——像流水账。第 1 条是 UI 逻辑错误，第 8 条是路径传递错误，第 10 条是窗口尺寸保存错误，第 24 条是 AI 替换代码的花括号丢失……它们像一堆散落在地上的钉子，大小不一、长短各异，但没有分类。

如果你问"YSM 世界里最常见的 Bug 类型是什么"，你得手动翻遍 38 条记录才能回答。

于是有人做了一个分类：

| 类型 | 数量 | 典型案例 |
|------|------|---------|
| 路径格式错误 | 8 | data-name vs data-path、Windows 反斜杠、相对路径 |
| 类型/零值陷阱 | 5 | Go bool 三态、base64 暗渡陈仓、BOM |
| Shadow DOM 隔离 | 4 | CSS 变量不继承、事件穿透不了、按钮失踪 |
| 同名冲突 | 4 | public/ 影子文件、pivots map 覆盖、inited 缓存 |
| CSS 视觉 Bug | 4 | 选中高亮消失、着色顺序反转、字号不统一 |
| AI 替换代码 | 3 | 花括号丢失、const 重赋值、逻辑写反 |
| 构建与部署 | 3 | wails build vs go build、resource_types.json 未打包 |

路径格式错误占第一位。8 条——几乎占了全部 Bug 的五分之一。

这不是巧合。YSM 模型管理器是一座巴别塔，Go 和 JS 和 C++ 通过路径传递文件引用。路径是桥上的货币——每一条消息都带着路径。而路径在每层边界上都有不同的格式：Go 用反斜杠，JS 用正斜杠，URL 只要正斜杠，Shadow DOM 里的 `data-path` 可能是绝对路径也可能是相对路径。

**最常见的 Bug 类型，恰好是跨边界传递中最脆弱的环节。**

这不是偶然，这是规律。

## 二 · Debug Path Review

比 Bug 分类更重要的是另一件事——**记录猜错了什么**。

`bug-chronicle.md` 里有一个特殊的栏目，叫 Debug Path Review。它不记录 Bug 本身，记录的是**排查过程中的错误推测路径**。

```
Issue: 整合包右键"从仓库导入"导入了所有整合包

Round 1 (Guess): 以为是 Go 端循环写错了。
Round 2 (Guess): 以为是 bus 事件发重复了。
Round 3 (Truth): 事件根本没传 instanceName。

Lesson: 先看数据源（Event Payload），再看循环体。
```

```
Issue: window.showConfirm 确认框不弹

Round 1 (Guess): 以为是 modal.js 没加载。
Round 2 (Guess): 以为是 Shadow DOM 作用域问题。
Round 3 (Truth): window.showConfirm 从未被挂载到 window 上。

Lesson: 全局函数调用不工作 → 先 console.log(typeof window.xxx)。
```

每一条 Review 都遵循同一个格式：Round 1-N 是猜，Round N+1 是真相，Lesson 是教训。

**为什么要记录猜错了什么？** 因为猜错比猜对更有价值。

猜对了，你只知道这个 Bug 的解法。猜错了，你知道了**哪种思考方式会把你带偏**。下次遇到类似症状，你会先避开上次猜错的方向。

Debug Path Review 是裂缝地图的等高线。它不只画了"缝在哪"，还画了"找缝时最容易走错的路"。

## 三 · 铁律

从 38 条 Bug 和 Debug Path Review 中，有人提炼出了一组铁律——不是建议，不是最佳实践，是**用痛苦换来的不可违反的规则**：

1. **显示名和路径名，必须分开存储，不可混用。** ——来自第一章。
2. **所有 JSON 读取必须去 BOM。** ——来自第三章。
3. **任何文件名匹配的代码，都必须先去 `.ban` 后缀再匹配。** ——来自第三章。
4. **按钮状态恢复事件始终放在 `finally` 块。** ——来自第六章。
5. **需要常驻监听的事件处理器必须放在 `app-content` 中。** ——来自 app-content 的坚守。
6. **所有新组件为 ESM，禁止在 `public/` 放 JS。** ——来自第二章。
7. **修改前确认最新状态——禁止基于记忆直接修改。** ——来自 AI 的教训。
8. **替换失败后禁止强行重试——先检查 import 语句。** ——来自 AI 的教训。
9. **跨语言数据传递每层验证 `typeof`。** ——来自第五章。
10. **废弃代码路径在 Bug 修复后必须重新评估。** ——来自第八章。

十条铁律，十条裂缝的地图。

它们不保证你不会再遇到 Bug——边界悖论是永久的。但它们保证你**不会再犯同一种错**。同一种症状可能由不同的根因引起，但同一种思考错误不会重复。

"铁律"这个词是刻意选的。不是"建议"——建议可以被忽视。不是"最佳实践"——最佳实践有例外。铁律没有例外。每一条背后都有至少一次"Round 1-3 猜错"的痛苦经历。

## 四 · 战斗手册

铁律被写进了 `copilot-instructions.md`——一份叫"战斗手册"的文件。

它不只是铁律的列表。它是一份完整的作战规程：

- **致命陷阱**：`.ban` 后缀、BOM、base64、`public/` 优先级——这些是地雷，踩一次炸一次。
- **工作流**：修改前先 grep 确认、改完立即 build 验证、不攒多个修改。
- **约定**：事件名格式 `scope:action`、扩展名集中定义、CSS 用变量不硬编码。

战斗手册是给谁看的？给 AI。

人类开发者靠肌肉记忆——犯过一次的错不会再犯。但 AI 没有肌肉记忆。每次醒来都是白纸。战斗手册是白纸上的第一行字——"先读这个，再动键盘"。

`AGENTS.md` 是入职指南，告诉你先读哪些文档。`copilot-instructions.md` 是战斗手册，告诉你哪些坑绝对不能踩。`bug-chronicle.md` 是编年史，记录了每一个坑的来历。`Design.md` 是设计规范，告诉你正确的做法是什么。

四份文档，四种功能，构成了裂缝地图的四个图层：

| 文档 | 图层 | 回答的问题 |
|------|------|-----------|
| AGENTS.md | 索引 | 先看什么？ |
| copilot-instructions.md | 危险区 | 哪里不能踩？ |
| bug-chronicle.md | 编年史 | 踩过了什么？怎么找到的？ |
| Design.md | 规范 | 正确的做法是什么？ |

## 五

`app.go` 看着四份文档，想起了第一幕的那个夜晚——`data-name` vs `data-path` 的裂缝被修好时，它以为"修好了就没事了"。

现在它知道了：修好了不是没事了。修好了一次，不代表下次不会犯。同一个形状的 Bug 会换一副面孔再出现——data-name 换成 data-dir，data-dir 换成 data-path，绝对路径换成相对路径，Windows 反斜杠换成 URL 正斜杠。

面孔变了，形状没变。形状就是：**跨边界的路径传递，每层都有自己的格式**。

铁律不能消灭形状。但铁律能让形状**在出现的第一时间被认出来**。

以前，一个路径格式 Bug 需要 3-8 轮 Debug 才能定位。现在，铁律第 1 条写在那里——"显示名和路径名，必须分开存储"。新 AI 读到它，下次写代码时就会把 `data-path` 和 `data-name` 分开。即使 Bug 还是出现了，Debug 路径也从"Round 1-3 猜错"缩短到了"看路径传递链路"。

8 轮 → 1 轮。不是消灭了 Bug，是**缩短了找 Bug 的时间**。

这就是绘图师的方式——不消灭裂缝，画一张地图，让裂缝在出现的第一时间被定位。

---

**缝**：Bug 的形状会反复出现——面孔变了，底层模式没变。铁律不是消灭形状，是缩短识别形状的时间。

**教训**：猜错比猜对更有价值，铁律无例外。
