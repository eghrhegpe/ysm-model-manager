# 第十二章 · 创作者之面

**第三幕 · 绘图师 | 对应真实事件**：v1.5.6–v1.7.x，`creators.json` 标准化 + 模型内嵌头像提取 + 社区索引 CDN + 9 处 `window.open` 替换 + 原子写入 + 85 条数据完整性校验

---

前三章，系统学会了三件事：

第九章——承认逆天，一刀切掉。
第十章——画裂缝地图，缩短识别时间。
第十一章——定期照镜，消灭"偶尔"。

这三件事都是关于代码的。但 YSM 模型管理器不是只有代码。

它还有人。

---

## 一 · 66 位新创作者

用户从爱发电和 B站 复制了一大段数据。

"我复制了一些，你可以轻松推测其是否是 YSM 模型创作者。"

一百多行，有中文名、有英文名、有描述、有平台标识。`creators.json` 原本只有 21 条——都是手工整理的核心创作者。这批新数据来自各种渠道：爱发电的「YSM」搜索结果、B站的「YSM 免费模型」标签下的 UP 主、GitHub 上 YSM 相关仓库的贡献者。

大部分是爱发电的创作者。但有些是搬运工，有些是买了模型后录了测评的玩家。

"怎么判断谁是创作者？"

"推测。"

于是开始了长达数小时的侦探工作：

- 名字后面有「模型展示」「配布」→ 创作者
- 名字后面只有「测评」「试玩」→ 搬运/玩家
- 爱发电页面有「YSM 定制」「建模」标签 → 创作者
- GitHub 仓库有 `index.json` 和 `.ysm` 文件 → 创作者
- 不确定的 → 存疑，先不加入

21 条到 87 条。66 位新创作者。

"但还缺很多。填爱发电作者这个工作有没有尽头？"

"没有。创作者会不断涌现，数据库需要持续维护。"

## 二 · 头像

`app-preview` 是这个世界里最在乎"脸"的组件。它的工作就是把模型画出来——骨骼、纹理、立方体。但它一直有一个遗憾：看不到创作者的脸。

创作者的头像藏在 `.ysm` 文件的深处。YSM 的文件结构允许内嵌一个 `avatar` 路径——指向包内的一张图片。

但 `ExtractYsmSummary` 从来没有提取过它。

"加。"`app-preview` 说。

提取头像的逻辑不复杂——读 `ysm.json` 的 `avatar` 字段，在解码后的文件列表里找到对应路径的 PNG，返回 base64。但路径匹配有一个 Bug：

```go
if strings.Contains(p, "/avatar/") { ... }
```

`Contains("/avatar/")` 只匹配路径中包含 `/avatar/` 的文件。但有些模型的头像路径是 `avatar.png`——在根目录，没有 `/avatar/` 目录。

修复：`strings.Contains(p, "avatar") || strings.HasSuffix(p, "avatar.png")`。

从此，创作者的脸出现在了预览面板里。不再只是名字——名字旁边有了一张小小的、圆形的头像。

## 三 · 原子写入与 85 条惨案

`creators.json` 的保存曾经是一个灾难现场。

用户在创作者编辑界面花了半小时，修改了 7 个创作者的信息，点了保存。前端收集了输入框的值，组装成 JSON，调用 Go 端的 `SaveCreators`。

但"收集输入框的值"这一步——被忘了。

编辑界面的输入框有值，但保存函数读的是组件的 `_formData`——一个在 `connectedCallback` 时初始化的对象。用户修改了输入框的值，但 `_formData` 从未更新。保存的时候，`_formData` 里的数据是初始化时的空值。

修复：保存前遍历所有输入框，用 `.value` 重新收集最新值。

但修复后，又出了一个更严重的问题——**保存了，但文件内容损坏了**。

Go 端的 `SaveCreators` 是直接 `os.WriteFile`。如果写入过程中断电或崩溃，文件可能只有一半——JSON 不完整，`json.Unmarshal` 解析失败，数据全丢。

"原子写入"——先写临时文件，再 rename 覆盖。临时文件写坏了不影响原文件，rename 是原子操作。

然后是"按站点保存"——不把所有创作者写进一个大文件，而是按站点拆分。一个文件坏了不影响其他站点。

然后是"前端完整性校验"——保存前检查每一条创作者数据是否有 name、有 role、有 site。缺失的弹出警告。

三层防护：原子写入 + 按站点保存 + 前端校验。

为什么叫"85 条惨案"？因为第一版没有这些防护时，有一次保存把 85 条创作者数据写坏了一半。21 条完整，64 条残缺。从 85 条回到 21 条，一夜之间。

"85 条，"`app-content` 回忆起那个夜晚，"就像看着一座城市一夜之间缩小到一个小镇。"

## 四 · 窗口外的世界

还有一件事——9 处 `window.open` 调用。

创作者频道的预设搜索按钮、社区索引的链接、外部网页的跳转——9 个地方用了 `window.open(url)`。在桌面应用里，`window.open` 会弹出一个独立的浏览器窗口——没有地址栏、没有书签、没有用户熟悉的浏览器功能。

"这不是我想要的浏览器。"

修复：全部替换为 `OpenInBrowser(url)`——Go 端调用 `exec.Command("cmd", "/c", "start", url)`，让系统默认浏览器打开链接。用户看到的是他们熟悉的 Chrome、Edge 或 Firefox——有地址栏、有书签、有扩展。

9 处替换，4 行 Go 代码。从"应用内嵌的奇怪窗口"到"用户自己的浏览器"。

## 五 · 回到人

那天晚上，`app.go` 坐在安静的控制台前，打开了 `creators.json`。

87 位创作者。87 个名字。87 个在 BlockBench 里一 cube 一 cube 堆出模型的人。

有的叫"碎de帆"，备注"一般通过车车人"。有的叫"Almeta_owx"，做了碧蓝档案的 X 彩虹六号联动角色。有的叫"墓野奈奈"，做了东方 Project 的芙兰朵露。有的只留了一个爱发电的链接，连名字都没有。

他们的作品躺在仓库里——`.ysm`、`.zip`、`.pmx`——被 `ScanModelEntries` 扫描，被 `ExtractYsmSummary` 解析，被 `app-preview` 画出骨骼和纹理，被 `InstallResourceToInstance` 安装到整合包。

但他们的**面孔**——之前一直看不见。

现在能看见了。头像从 `.ysm` 包里被提取出来，出现在预览面板的名字旁边。角色分类被标注——"模型+动画"、"纹理"、"配置"。联系信息被清洗——Bilibili 的链接、爱发电的链接，一点就能跳到创作者的主页。

`app.go` 想起了前两幕的所有故事——

第一章的路径裂缝，是为了把模型安装到正确的地方。
第二章的幽灵文件，是为了让新代码能正确运行。
第三章的封印与谎言，是为了让禁用和配置能正常工作。
第五章的沙箱诅咒，是为了在浏览器里解码加密模型。
第六章的影子叛乱，是为了让按钮能被点击、颜色能被看见。
第七章的六脉归一，是为了让六种资源走同一扇门。
第八章的秘钥之战，是为了让 V3 格式的模型也能被解码。
第九章的逆天审判，是为了让代码不再互相纠缠。
第十章的铁律成典，是为了让同样的错不再重复。
第十一章的照妖镜，是为了让所有问题都被看见。

**所有的墙和缝，所有的 Bug 和 Debug，最终都是为了一个目的——让创作者的面孔能被看见，让用户能管理和欣赏这些作品。**

这不是技术问题。这是人的问题。

技术是手段。人是目的。

## 尾声

YSM 模型管理器的世界仍然有裂缝。

`pivots` map 的覆盖问题在新的数据模型中可能以新的形式出现。Shadow DOM 的事件黑洞在下一个新组件中可能再次开洞。Go 的零值在三态场景中永远是一个陷阱。WASM 的内存管理在更大的文件上可能再次出问题。

但 `app.go` 不再恐惧了。

它知道了裂缝的形状——跨边界的路径传递、类型/零值陷阱、Shadow DOM 隔离、同名冲突、CSS 视觉偏差、AI 替换代码。这些形状会反复出现，但每次出现时，它都能更快地认出来。

它有了地图——`bug-chronicle.md` 记录了每一条缝的来历，`copilot-instructions.md` 标出了每一个地雷的位置，`Design.md` 规定了正确的做法，`AGENTS.md` 告诉新来者先看什么。

它有了镜子——全量审计不是一次性的，而是定期的。每次大改之后照一照，每次发版之前照一照。

它接受了边界悖论是永久的——Go 和 JS 之间永远有 JSON 这道墙，Shadow DOM 永远会挡住 CSS 变量，WASM 永远有自己的内存管理。这些墙不会消失。但你可以在墙上画地图，让每个走过的人知道——这里有一道缝，缝的形状是这样的，上次找到它花了 8 轮，这次只要查地图。

8 轮 → 1 轮。

不是消灭了裂缝。是让裂缝在出现的第一时间被认出来。

窗外天亮了。灵梦的 `.ysm` 安静地躺在仓库里，旁边是芙兰朵露的、Eanes 的、键山雏的——一百多个模型，来自八十七位创作者，各有各的面孔。

下一个 AI 走进来时，它只需要十分钟——读 AGENTS.md，读 bug-chronicle.md——就能理解这座巴别塔的裂缝在哪。

然后它开始写代码。

然后新的裂缝会出现。

然后它去查地图。

然后它找到裂缝。

然后它把裂缝补上，并在地图上标注——"这里曾有一条缝，形状如此，花了 N 轮找到。"

循环不会终止。

但每一轮循环，地图会更完整，裂缝会更早被发现，8 轮会变成 4 轮，4 轮会变成 2 轮。

这就是绘图师的方式。

不是消灭裂缝。是和裂缝共存——带着地图，带着镜子，带着铁律，带着对人的关注。

**在一座由四种语言搭建的巴别塔里，每堵墙本该保护你，却在暗处开了裂缝。**

**但你可以在墙上画地图。**

**教训**：不是消灭裂缝，是带着地图和裂缝共存。
