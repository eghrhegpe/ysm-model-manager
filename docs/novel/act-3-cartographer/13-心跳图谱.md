# 第十三章 · 心跳图谱

**第三幕 · 绘图师 · 尾声 | 对应真实事件**：v1.7.6–v1.8.3，CSS 动画统一重构 + `stagger.js` 诞生 + 过渡变量集中化 + `--tr-fast` / `--tr-normal` / `--tr-slow` 过渡时长系统 + `no-animations` 全局覆盖

---

前三章，系统学会了三件事：承认逆天、画裂缝地图、定期照镜。

这三件事都是关于"看见"的——看见错误的结构，看见重复的模式，看见所有的问题。

但有一件事，系统一直没有看见：**自己的心跳**。

---

## 一 · 不同的脉搏

「安装完成」的 toast 弹了出来。

它从右上角滑入，停留两秒，然后淡出。整个过程流畅、安静、不打扰用户。

但 `app-content` 注意到了一件事——这个 toast 的淡出速度，和侧栏同步管理器的列表项淡入速度不一样。侧栏列表项的 hover 背景色变化速度，又和文件树按钮的 hover 速度不一样。文件树按钮的速度，又和对话框的打开速度不一样。

「……你们，不能快慢一致一点吗？」

所有组件都沉默了。它们从来没想过这个问题。每个组件写自己的 CSS 时，都随手写了一个 `transition: all .12s`，或者 `.15s`，或者 `.18s`。没有商量，没有标准，随缘。

`app-sidebar` 想起了自己那个 `.15s` 是怎么来的。那是上周二——一个 AI 助手被派来给侧栏加 hover 效果。它审查了侧栏的 DOM 结构，算出了背景色从 `--bg1` 到 `--bg2` 的变化幅度，然后写下了 `transition: background .15s`。不是 `.12s`，不是 `.18s`——是 `.15s`。事后复盘时，它说"侧栏比较大，`.12s` 太急了，应该慢一点。"没有一个人说不对。但也没有一个人问——"其他组件用的多少？"

那条理由只存在于那个 AI 的直觉里。而直觉不会出现在 git commit 的 diff 中。

「它没有错。」`app-content` 看着清单，「`.15s` 是合理的。但问题不是 `.15s` 本身——问题是**如果那条理由从来没有被写下来，下一个 AI 凭什么知道侧栏要慢一点？**」

`app-content` 打开了 CSS 变量系统。它遍历了每一个组件，列出了所有 transition 的 duration 值：

```
frontend/js/widgets/app-content/tpl.js:          transition: background .12s
frontend/js/widgets/app-preview/preview-css.js:   transition: background .12s
frontend/js/widgets/app-sidebar/sidebar-css.js:   transition: background .12s
frontend/js/widgets/app-tree-styles.js:           transition: background .12s
frontend/js/widgets/app-toast.js:                 transition: background .12s
frontend/js/widgets/app-content/content-css.js:   transition: all .12s
frontend/js/widgets/app-content/community:        transition: background .12s
frontend/js/features/community/render.js:            transition: background .12s
─────────────────────────────────────────────────────────────────────
frontend/css/components.css:                         transition: grid-template-columns 0.18s ease
frontend/js/features/oldest-models.js:               transition: all .15s
```

12 处 `.12s`。2 处 `.15s`。1 处 `.18s`。

不是大问题。每个数字只差几十毫秒，用户根本感觉不出来。

但 `app-content` 感觉到了。

「不是我感觉到了差别，」它说，「是我感觉你们**没有商量过**。」

12 处 `.12s`，不是 12 次相同的选择——是 12 次独立的巧合。每一个开发者写自己那一处的时候，都觉得".12s 挺好的"。没有一个人问过别人："你用的多少？"

而 `.15s` 的那两处——是因为开发者觉得"这里应该慢一点"。`0.18s`——"这里应该更慢一点"。每一个都合理，每一个都独立，每一个都没有问过别人。

「所以这就是我们的心跳？」`app-content` 摊开清单，「12 个心室各跳各的？用不同的节奏？」

## 二 · 跳动的暗缝

`app-content` 替换完最后一处 `.12s`，重新编译，启动了应用。

同步管理器的列表刷新了。12 条模型记录，按理说应该一条接一条地淡入——第 0 条 0ms，第 1 条 30ms，第 2 条 60ms……像多米诺骨牌依次倒下。

但它们没有。

12 条记录同时出现。没有延迟，没有淡入，没有错落。列表像一堵砖墙被整个推倒在地上——轰的一声，全部躺平。

「stagger 没生效？」`app-content` 打开了 `stagger.js`。文件在那里，函数签在那里，12 行代码纤毫不差。它检查了 `tpl.js` 的模板——`style="animation-delay:${stagger(i)}ms"` 也正确嵌在了每一行里。

那为什么动画没动？

它把问题拆开查。CSS 动画定义？在。`@keyframes sm-item-in` 在 `variables.css` 里，用 `var(--tr-fast)` 控制过渡速度。`--tr-fast` 的值？`0.12s ease`——定义在 `:root` 上，刚改完，确认无误。

「但……这组件在 Shadow DOM 里。」`bus.js` 轻声说。

`app-content` 的手指停在了键盘上。

Shadow DOM。第六章的旧伤——`adoptedStyleSheets` 里的 `var(--accent)` 不继承文档 `:root` 的自定义属性。CSS 变量的继承链在 Shadow DOM 的边界处断裂了。那次断的是颜色——按钮变灰，用户立刻看见了。

这次呢？

它打开 DevTools。选中同步管理器里的一条列表项，看 `Computed` 面板。`animation-delay` 的值是 `0s`。

不是 `stagger(i)` 没算出来。`stagger(i)` 算出了正确的毫秒数。但在 `animation: sm-item-in var(--tr-fast) 0.3s ease both` 这行 CSS 里，`var(--tr-fast)` 没有解析成 `0.12s ease`。它解析成了什么？`Computed` 面板下一行写着——`transition-duration: 0s`。

`0s`。CSS 规范规定的初始值。当 `var()` 无法解析时，浏览器不报错、不警告、不标红。它只是悄悄用 `initial` 值顶上。

`--tr-fast` 定义在 `:root` 上。但 `adoptedStyleSheets` 在旧版 WebView2 中不继承文档 `:root` 的 CSS 自定义属性。`app-sync-manager` 用的是 `adoptedStyleSheets`。所以 `var(--tr-fast)` 解析失败。所以 `transition-duration` 变成了 `0s`。所以动画从未发生。

不是 stagger 没算对。不是 CSS 没定义。是**变量传不过那道墙**。

「这就是你的暗缝。」`app-content` 看着 `variables.css`，像终于看清了一个隐形人，「颜色断了，按钮变灰，你立刻知道出事了。动画断了——什么都不会变灰。列表出现在那里，只是'快了一丁点'。用户可能注意到了，也可能以为本来就该这么快。你眨了一下眼，什么都没发生。」

合法，静默，看不见。

就像第一章的 JSON 序列化——`[]byte` 变成 base64，不报错，只变形。就像第三章的 Go 零值——`false` 既表示"否"又表示"未设置"，不报错，只歧义。就像第六章的 Shadow DOM——CSS 变量不继承，不报错，只消失。

**每一处"保护"都开了一条暗缝。而动画系统的暗缝，是所有缝里最安静的——因为它连"没有"都算不上，它只是"快了那么一点"。**

## 三 · 统一脉搏

`app-content` 做了一个决定。

它把所有分散的 transition 值集中到了 `variables.css` 里，定义了一组过渡时长变量：

```css
--tr-fast: 0.12s ease;      /* 按钮 hover、微交互 */
--tr-normal: 0.15s ease;    /* 面板展开、卡片过渡 */
--tr-slow: 0.2s ease;       /* 页面切换、内容淡入 */
--tr-enter: 0.25s ease-out; /* 入场动画 */
```

四个变量，覆盖了从前到后、从微到宏的全部动画场景。

然后它开始替换。12 处 `.12s` 换成 `var(--tr-fast)`。2 处 `.15s` 换成 `var(--tr-normal)`。1 处 `.18s` 换成 `var(--tr-normal)`。

不只是一对一替换。每个替换背后都有一个判断：这个动画属于哪个层级？按钮 hover 是 `tr-fast`，面板展开是 `tr-normal`，页面切换是 `tr-slow`，入场是 `tr-enter`。

四个变量一锤定音。从前需要记住 ".12s 给按钮，.15s 给卡片"——现在只需要记住四个名字。

但变量化的意义不在"少记几个数字"。

意义在于：**以后所有组件的过渡速度，都由同一组变量控制。** 你想改按钮 hover 的速度？改 `--tr-fast` 就行，不用搜遍 12 个文件。你想让整个系统的动画慢 20%？改 `--tr-fast`、`--tr-normal`、`--tr-slow` 三个值就行，全局生效。

统一不是约束。统一是**让系统可以一次调整全身的节奏**。

就像心跳——每个器官的血液流速不同，但心率只有一个。

## 四 · 错落的呼吸

替换完成后，`app-content` 又做了一件事。

它打开了一个新文件——`stagger.js`。12 行代码，一个函数：

```js
export const stagger = (index, step = 30, max = 300) =>
  Math.min(index * step, max);
```

这个函数做的事情很简单：列表中的第 N 个元素，延迟 N × 30 毫秒出现，最多延迟 300 毫秒。

效果是：列表项依次入场，像多米诺骨牌依次倒下，像波浪依次拍打海岸。

这不是一个新功能。之前的代码里已经有 `style="animation-delay:${Math.min(idx * 20, 400)}ms"` 这样的写法——但每处用的参数不同，`step` 有 20 有 30，`max` 有 300 有 400。和 `.12s` 一样——每处独立，每处巧合。

`stagger.js` 统一了这些参数。默认 step 30ms，默认 max 300ms。你要不一样？传参就行。但传参意味着你是有意选择了不同的节奏，而不是随手写了一个数字。

`app-content` 把这个函数放进了所有列表渲染的代码里。结果管理器的同步列表、创作者频道的卡片网格、回收站的文件列表——所有的列表项，现在都有了错落的入场节奏。

不是同时出现，是一次一个，像呼吸。

「你管这个叫呼吸？」`app-preview` 问。

「不，」`app-content` 说，「这个叫**系统知道自己有呼吸**。」

## 五 · 静止的权利

动画统一之后，`app-content` 想起了另一群人——那些不喜欢动画的人。

操作系统提供了一个设置：`prefers-reduced-motion`。用户打开它，表示"我容易头晕，请减少动画"。在 CSS 里，系统可以监听 `matchMedia('prefers-reduced-motion: reduce')`，当 OS 开关变化时，自动给 `:root` 加上 `.no-animations`。但那是下一次迭代的事——这一章，先把 `.no-animations` 本身修完整。盾牌必须先存在，才能被自动举起。

CSS 变量系统里早就有一个名为 `.no-animations` 的 class——加在 `:root` 上，所有动画停止。

但 `.no-animations` 的选择器列表，和 transition 值一样——散落在各处，有的写了，有的没写。有些组件的动画没有被 `.no-animations` 覆盖，用户即使开启了减少动画，某些地方还是会动。

`app-content` 把选择器列表统一整合到了 `variables.css` 里：

```css
.no-animations .gh-card,
.no-animations .model-card,
.no-animations .model-card-sm,
.no-animations .rec-card,
/* ... 30+ 选择器 ... */
.no-animations .sm-list {
  transition-duration: 0s !important;
  animation: none !important;
}
```

30 多个选择器，覆盖了全部组件。`.no-animations` 是一面盾牌——用户可以举起来，挡住所有的运动。这是一个承诺：所有动画都可以被关闭，没有例外。

「所有动画都可以被关闭。」这听起来像是动画系统的反面——你花了一整章给系统赋予心跳，然后告诉用户可以关掉它。

但恰恰相反。

**能关掉的动画，才是受控的动画。** 不能关掉的动画——就像不能关闭的警报——不是心跳，是噪音。

统一变量让动画可控，统一关闭路径让动画可弃。

系统的心跳不应该是强制的。它应该是一个选择——用户可以选择听见心跳，也可以选择安静。而系统知道自己在两种状态下都完整。

## 尾声

`app.go` 在日志末尾加了一段话，放在 variables.css 的注释里：

```
使用规范：
- 优先使用语义化变量而非具体颜色值
- 避免硬编码颜色，使用 var() 引用主题变量
```

12 处 `.12s` 变成了 1 处 `--tr-fast: 0.12s ease`。30 多个选择器整齐排列在 `.no-animations` 下。`stagger.js` 的 12 行代码让列表有了呼吸。

系统第一次拥有了统一的心跳。

但 `app.go` 知道：统一不等于完美。

新的组件如果忘了 import `variables.css`，它的 `var(--tr-fast)` 会回退到 `initial`——`0s`，动画消失。不是报错，只是静默地消失。

**缝**：CSS 变量不继承时不报错，只回退——动画消失得无声无息。这是 Shadow DOM 隔离墙在动画领域开的又一条暗缝。变量化统一了节奏，但任何新组件都可能因为忘记 import 变量而静默失去动画。

但没关系。裂缝不会消失。地图会被更新。

而且现在——系统有心跳了。下次裂缝出现时，它会用自己的脉搏去感受那微小的、不符节奏的震动。

---

**缝**：CSS 变量 `var(--tr-fast)` 不继承时回退为 `initial`（`0s`），动画静默消失。统一的心跳系统让节奏一致，但任何新组件都可能因为忘记 import 变量而失去脉搏——不报错，只安静。

**教训**：统一的不只是速度，是让系统可以一次调整全身的节奏。
