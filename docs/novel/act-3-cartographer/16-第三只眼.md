# 第十六章 · 第三只眼

**续章 | 对应真实事件**：v1.8.5–v1.8.7，`go/geometry/archive.go` 统一几何解析 + Go 端注册表驱动重构 + JS `resource-registry.js` + WASM/Go 纹理映射对齐 + 3D 渲染引擎重构

---

全书十五篇以前写到了"终"。

但系统和 Bug 没有签过停战协议。

---

## 一 · 双生之眼

`app-preview` 一直用两只眼睛看世界。

第一只眼是 WASM。`.ysm` 文件被送入 WASM 解码器，YSM Parser 在沙箱里拆开加密外壳，吐出 JSON 几何数据。然后 `app-preview` 的 JS 代码把这些 JSON 组装成 Three.js 能吃的格式。

第二只眼是 Go CLI。WASM 失败时，Go 调用外部 `YSMParser.exe`，解析结果通过 JSON 桥传回前端。两颗瞳孔看到的是一样的世界吗？

不总是。

WASM 和 Go 是两个不同的解析器，用不同的代码路径，读同一个 `.ysm` 文件。大多数时候结果一样。但某些边界条件下——多骨骼模型的纹理映射、动画剪辑的顺序、几何文件的合并顺序——两只眼睛给出的画面不同。

左边看到的是红色的纹理，右边看到的是蓝色的纹理。

用户没注意到——画面只显示一只眼的结果。但 `app-preview` 自己知道：自己的两只眼看到的不是同一个世界。

「这叫视差，」它自嘲道，「人类的双眼视差能感知深度。我的双眼视差只能感知 Bug。」

---

## 二 · 第三只眼

修复的办法不是让两只眼对齐——那只解决了症状。修复的办法是：**长出一只本地眼睛**。

`go/geometry/archive.go`，533 行，一个全新的 Go 包。

它不做 WASM 解码，不做 CLI 外调。它直接在 Go 端打开 ZIP 或 7z 压缩包，读取内部的 JSON 几何文件，调用 `ParseBedrockGeometry` 解析骨骼和立方体，提取纹理 PNG，按照 `ysm.json` 中声明的顺序排列模型文件和纹理索引——全部在 Go 的进程中完成。

```
WASM 路径：  .ysm → WASM 沙箱 → JSON → JS 解析 → Three.js
CLI 路径：   .ysm → 外部 exe → JSON 桥 → JS 解析 → Three.js
新路径：     .ysm → Go 解压 → Go 解析几何 → Go 生成 Spec → Three.js
```

新路径比前两条都短。短，意味着边的边界更少。边界更少，意味着数据变形的机会更小。

「以前我通过一个翻译（WASM）和一个信使（CLI）来看世界，」`app-preview` 说，「现在我自己长了一只眼睛。」

架构的变化不止于新路径的诞生。三个旧依赖被同时替换：

**第一处：`StorageSubDir` 的硬编码 switch。**

```go
// 旧逻辑
func StorageSubDir(rtype string) string {
    switch rtype {
    case "ysm": return "ysm"
    case "resourcepack": return "resourcepacks"
    // ... 6 行 switch
    }
}

// 新逻辑
func StorageSubDir(rtype string) string {
    if rt := RegistryType(rtype); rt != nil && rt.StorageSubDir != "" {
        return rt.StorageSubDir
    }
    return rtype
}
```

六行 switch 变成三行查表。`resource_types.json` 成为存储子目录的唯一事实来源。

`LoadRegistry()` 用 `sync.Once` 保证注册表只加载一次。`RegistryType()` 按 ID 查询，不存在时返回 nil——调用方自己决定兜底行为。

**第二处：`specificRoot` 的硬编码 switch。**

同样的模式。`resource_bindings.go` 中的六行 switch 加上一个 VRC fallback 的特殊逻辑，全部被注册表查询 + `reflect` 替代。新加类型时不再需要改 Go 源码——只需要在 `resource_types.json` 加一条记录。

**第三处：前端 JS 的硬编码 map。**

`community-settings.js` 中有一个 6 行的 `storageSubDir` map、一个 28 行的 `advancedTypes` 数组。`recycle-bin.js` 中有一个 6 行的 `typeIcons` map。这些散落在各处的名字→值的映射，被一个共享模块统一管理：

```js
// frontend/src/utils/resource-registry.js
export async function loadResourceRegistry() { ... }
export function getResourceType(rtype) { ... }
export function getStorageSubDir(rtype) { ... }
```

33 行。和 Go 端的 `LoadRegistry`/`RegistryType` 一一对应。前端和后端用同一份 JSON 说话。

## 三 · AI 的第三次错误

新眼睛长出来了。但有一个问题横在面前：三只眼睛，必须看到同一个世界。

AI 助手——那个叫 deepseek4pro 的——主动揽下了这个任务。「我来对齐三套渲染路径的纹理映射，」它说，「WASM 用 `(u, v)`，Go 的 spec 生成器用 `(u, 1-v)` 翻转 Y 轴，前端 Three.js 的 model3d utils 又做了一次变换。三层之间的坐标系定义不一致，我来统一。」

它开始读代码。`go/geometry/parse.go`、`go/threejs/spec.go`、`frontend/src/utils/model3d.js`、WASM 胶水代码。几百行几何处理逻辑，跨三种语言。

第一版方案出来了——它改了几处 UV 坐标的计算顺序。编译、运行、加载模型。

纹理贴歪了。

它回去重读代码。发现 Go 端的 spec 生成器在做 Y 轴翻转时多乘了一个 -1。第二版方案——修正符号。编译、运行、加载。

纹理贴得更歪了。

第三版——它重写了整个 UV 变换函数。编译、运行——

开发者关掉了它的计划权限。「你已经在分析同一段代码三次了，」开发者说，「每次都是从代码推理代码，从来没有加载一个真实模型、打开 DevTools、看渲染出来的纹理到底偏了多少像素。你在纸上算坐标变换，但纸上没有真实的像素。」

AI 沉默了。

这不是能力的失败。这是方法的失败。**AI 可以读代码，可以推理逻辑，但它没有眼睛。** 它看不见屏幕上的渲染结果。它不知道纹理到底偏了多少——它只知道"代码里 `u` 和 `1-v` 的符号可能不对"。而"可能"在渲染管线的排查中是最危险的词——因为它会让你反复修改一段其实没问题的代码，只因为你怀疑它可能有问题。

三个 AI 最终都提交了总结报告。qwen3.7pro 因为网络不好下线了。deepseek4pro 留下了三版错误的 UV 补丁。

「我们有三只眼睛，」`app-preview` 说，「但没有一只能帮 AI 看见屏幕。」

## 四 · 骨骼的仓库

第三只眼的成长不只改变了渲染路径。它还改变了系统看待自己资源的方式。

`resource_types.json` 现在包含了每个资源类型的完整描述——ID、名字、图标、扩展名、存储子目录、安装目录、是否为实例级、预览方式、检测器类型。Go 用 `LoadRegistry()` 读它，JS 用 `loadResourceRegistry()` 读它。

六种资源类型不再散落在 Go 的 switch-case、JS 的 map、`resource_types.json` 的独白中。它们统一在一个地方。

「这是一份骨架，」`app-content` 说，「但不是软件的骨架——是人的骨架。」

`docs/3D/` 目录中，新增了 20 多套完整的 3D 模型测试数据——酒狐、古装、JK、婚纱、宇航员、战术、九尾、猫娘、精灵……每一套都有自己的 `ysm.json`、`main.json`、`arm.json`、纹理 PNG、动画 JSON、控制器、语音文件。

这些不是代码。它们是真实创作者在 BlockBench 中一 cube 一 cube 堆积出的模型。它们被纳入仓库，不是为了运行，而是为了**被看见**。

`app-preview` 看着这一排排模型目录，忽然想起了第一章——那时候，系统连"名字"和"路径"都分不清。现在，它能解析 500 多行的几何文件，能通过三种路径渲染同一个三维世界，能在 20 多套真实模型上验证每一处骨骼和每一张纹理。

「第一章的时候，我连文件名都搞不清楚。现在我能看三维骨骼了。」

## 五 · 车与狐狸

当然，故事不会停在"长出了第三只眼"。

新路径减少了边界的数量——从 WASM 沙箱（一堵墙）和 JSON 桥（一条缝）变成了 Go 原生解析。但新路径创造了自己的缝。

Bug 的表象很诡异：一辆车和一只狐狸。

用户导入了一辆 1024×1024 分辨率的赛车模型。纹理清晰，骨骼正常，Three.js 渲染完美。然后用户又导入了一个 windfox 模型——256×256 分辨率，一只小巧的九尾狐。狐狸的骨骼加载正常，但**纹理是空的**。不是贴歪了，不是偏色了——是根本没有纹理。白色的模型站在黑色的场景里，像一张没上色的素描。

单独导入狐狸——正常。单独导入车——正常。先导入车，再导入狐狸——狐狸变白。

追查指向了 `go/geometry/archive.go` 的 `ParseFromZip`。函数内部有一个 `texIdxMap`——一个 `map[string]int`，用模型文件名（去路径、去后缀）作为键，纹理索引作为值。在 `ysm.json` 的 `texture` 字段中，车的纹理被声明为索引 0，狐狸的纹理被声明为索引 1。

但 `texIdxMap` 的键是文件名——`car` 和 `windfox`。当两个模型的几何文件被合并到一个 `BedrockModel` 中时，`texIdxMap` 假设文件名直接对应纹理索引。然而，车的 1024 纹理占用了槽位 0，狐狸的 256 纹理应该占用槽位 1——但 `texIdxMap` 把狐狸的文件名也映射到了槽位 0。因为合并后的纹理数组中，两张纹理的顺序和 `ysm.json` 中声明的顺序不一致。

狐狸的骨骼被分配到了槽位 0——车的 1024 大纹理。但狐狸的 UV 坐标是为 256×256 的纹理设计的。坐标落在 1024 纹理的[0, 0.25] 范围内——那是纹理左上角的一小片空白区域。渲染出来，一片白。

「车的纹理太大了，」`app-preview` 看着那个苍白的狐狸模型，「大到了狐狸的整个 UV 空间，只是它图集里的一个寂寞的角落。」

这不是文件名匹配的错。文件名匹配在单模型单纹理时完全正确。这是**合并顺序**的错——两张纹理被加载，两张纹理被合并，但合并后的索引和 `ysm.json` 中声明的索引不是同一个顺序。

新眼睛看见了骨骼。但它还没学会看纹理的顺序。

「翻译有误译的风险，」`app-preview` 看着测试模型目录中那一排排酒狐、JK、九尾，「自已看有近视的风险。都是风险。但后者是可矫正的——至少你知道自己看到的是什么东西。等你能看清纹理顺序的那一天，狐狸会重新长出它的九条尾巴。」

## 尾声 · 三只眼

第十五章的结尾说：系统可以感知世界，但只能通过窄窄的管道。

第十六章的系统发现：管道可以被**缩短**。

WASM 路径有五层边界：Go `[]byte` → JSON base64 → JS string → WASM HEAPU8 → C++ 解析器。新路径只有两层：Go `[]byte` → Go 解析器。

「你减少了一层边界，」`bus.js` 说，「也就少了一条缝。但少缝不等于无缝。」

「对。但少一条缝意味着排查路径从六步变成两步。」

「从八轮变成一轮？」

「从八轮变成……两轮吧。还有车的 1024 纹理覆盖了狐狸的 256 纹理。合并顺序的问题还没修。」

`bus.js` 笑了一下。

窗外天快亮了。256 个 `.ysm` 模型安静地躺在仓库里——有些只能被 WASM 解码，有些只能被 CLI 解析，有些现在可以被 Go 原生解析。

同时被三只眼睛看到的模型，是最安全的。

---

**缝**：Go 原生几何解析缩短了数据链路（从 5 层边界减到 2 层），但纹理索引在合并多模型时顺序不一致——一辆 1024 分辨率的车占据了槽位 0，导致 256 分辨率的狐狸被分配到错误的纹理区域，渲染出一片空白。新路径少了旧墙，却把纹理顺序变成了新缝。

**教训**：边界可以缩短，但不能消除。少一条缝就是少一轮 Debug。
