> 区域归属：`appendix/Go后端`（`internal/app/app_*.go` `go/download/` `go/avatar/` `go/sync/`）
> 时间线标签：vol-4

## 一 · 跑不了的测试

`internal/app` 是一栋很大的房子。

`app_download.go` 318 行。`app_avatar.go` 488 行。`app_scan.go` 577 行。`app_files.go` 337 行。`resource_bindings.go` 414 行。

以及 `app_install.go`——**1,315 行**。

加起来 4,609 行。

它们全都是 Wails 的 Binding 层。它们的职责本来应该很窄：接住前端的调用，转成 Go 的类型，交给后端逻辑，把结果转回去。一层薄薄的翻译膜。

实际上，业务逻辑全长在膜里了。

HTTP 下载、进度计算、头像提取与缓存、文件扫描与哈希、安装链接与回收站、配置保存、类型检测——全在 `app_*.go`。

而这些文件 `import` 了 Wails runtime。

于是：

```
go test ./internal/app/
```

跑不了。

不是失败，是**跑不起来**。Wails runtime 需要一个真实的窗口环境，测试进程里没有。

`app.go` 后来给这个状态算过一笔账，这笔账被原样写进了 ADR-003：

> AI 改了逻辑后无法用 `go test` 验证，必须人肉开 WebView2 窗口测。
> 一次误改 + 一次编译 + 一次开 app = **10 分钟**。一天改 5 次 = **50 分钟**浪费。

一天 50 分钟。这不是效率问题，这是**反馈回路的长度**问题。

十分钟的反馈延迟会改变一个人写代码的方式。你会倾向于一次改多一点——反正都要等十分钟。而一次改多一点，意味着出问题时你有更多的嫌疑犯。于是排查更慢，于是下次更想一次改多一点。

**长反馈回路会自我强化。**

## 二 · 薄壳与内核

ADR-003 的处置叫「Logic Sinking」——逻辑下沉。

模式很简单：**薄壳 + 内核**。

```
internal/app/app_download.go（薄壳 ~30 行）
  仅处理 Wails 事件发射 + 类型转换
        ↓ 调用
go/download/downloader.go（内核 ~200 行）
  纯 HTTP 下载、进度计算、文件保存
        ← go test 可测
```

分界线画在一个地方：**是否依赖 Wails runtime**。

依赖的，留在壳里。不依赖的，全部沉到 `go/` 包。

沉下去的东西，立刻获得了一样它此前从未有过的东西——**可测性**。

各文件的可提取比例被逐个估过：`app_avatar.go` ~95%（0 处 runtime 依赖）、`app_download.go` ~85%（10 处 EventsEmit）、`app_install.go` ~80%、`app_files.go` ~75%、`app_scan.go` ~70%、`resource_bindings.go` ~20%。

`app_avatar.go` 那个 95% 最刺眼。488 行代码，几乎全都是纯逻辑，一处 Wails 依赖都没有。

它躺在 Binding 层里，不是因为它需要在那儿。

是因为**它当初就是在那儿被写出来的**，之后没人问过它为什么还在那儿。

`app.go` 觉得这是整份 ADR 里最值得记住的一条观察：**代码的位置很少是被决定的，它通常只是被继承的。** 第一个人在哪儿写了第一行，后面所有相关的行就都长在那儿。

## 三 · 事件是唯一的绳子

下沉过程中最难切的，是 `app_download.go` 里那 10 处 `EventsEmit`。

下载器需要报告进度。报告进度需要发事件。发事件需要 Wails runtime。

于是整个下载逻辑被这 10 个点钉死在了壳里。

解法是老套但有效的——**回调注入**。内核不认识 Wails，它只认识一个函数：

```go
type ProgressFunc func(done, total int64)
```

壳负责把这个函数实现成 `EventsEmit`。内核负责在合适的时候调它。

内核从此不知道自己的进度会去哪儿。它可能去了前端，可能进了日志，可能在测试里被塞进一个 slice 用来断言。它不关心。

**依赖倒置的本质不是「反过来依赖」，是「让高层定义契约，让底层不知道自己被谁用」。**

沉下去之后，`go/download`、`go/avatar`、`go/sync` 都能直接 `go test`。反馈从十分钟压缩到几秒。

## 四 · RE2 的沉默

Go 后端还有一类痛，跟架构无关，跟**语言**有关。

```
panic: regexp.MustCompile: (?!(...)):
  error parsing regexp: invalid or unsupported Perl syntax: `(?!`
```

`proxy.go` 里写了一个带负向前瞻的正则：

```go
re := regexp.MustCompile(`(?i)((?!src|href)\w+)="(/[^"]+)"`)
```

这个正则在 JavaScript 里能跑，在 Python 里能跑，在 PCRE 的任何一个方言里都能跑。

在 Go 里 panic。

因为 Go 用的是 **RE2 引擎**。RE2 不支持前瞻 `(?!`，也不支持后顾 `(?<=`。

这不是缺陷，是设计取舍：RE2 保证线性时间匹配，代价是放弃回溯类特性。它换来的是**永远不会因为一个恶意正则把 CPU 打满**。

但对写代码的人来说，这个取舍是在运行时才被告知的。`regexp.MustCompile` 在包初始化时 panic——程序连启动都启动不了。

修法是退回到朴素的方式：

```go
func isAbsolute(u string) bool {
    return strings.HasPrefix(u, "http://") ||
           strings.HasPrefix(u, "https://") ||
           strings.HasPrefix(u, "//")
}
```

不优雅。但它能读懂，能测试，能在编译期被类型系统看管。

`app.go` 后来在 bug-chronicle 的通用教训里给它留了一行：**Go RE2 不支持前瞻/后顾，用辅助函数替代。**

它私下的注解更长一点：一个复杂正则能表达的东西，几乎总能用三个有名字的小函数表达。区别在于，正则把逻辑压缩进一串符号里，而函数把逻辑摊开成可以命名、可以单测、可以被下一个人读懂的东西。

**压缩率高的代码，解压成本也高。而解压的人通常不是写它的人。**

## 尾声

Logic Sinking 的 P0 到 P3 全部完成那天，`app.go` 瘦了很多。

它想起 ADR-001——升级 Wails 3 的那次迁移。那次它学到的是 API 会变；这次学到的是**位置会锁死能力**。

一段代码放在哪个包里，决定了它能被谁测试、能被谁复用、能被谁看见。这件事跟代码写得好不好完全无关。一段完美的逻辑，放在一个 `import` 了 GUI runtime 的文件里，就永远只能靠人肉点击来验证。

它不是被写坏了，它是**被关起来了**。

而囚禁它的不是恶意，是路径依赖。第一版功能最快的写法就是直接写在 Binding 里——反正只有几十行。然后几十行变成几百行，几百行变成 1,315 行，而搬家的成本随行数增长，搬家的意愿随成本下降。

「技术债的利息，」它想，「是以行数计的。」

它翻开 ADR-034，看见剩余债清单上还写着：24 个 Go 包，3 个零测试。

那 3 个包也在生产环境里跑。

它把这一页折了个角。

**缝**：可测性不是代码的属性，是代码所在位置的属性。同一个函数，换一个包就能被测试——这意味着「测试覆盖率低」这个症状，根因往往在架构分层，而不在测试写得少。

---

**教训**：跑不了测试的逻辑等于没被验证过，代码的位置决定它的命运。
