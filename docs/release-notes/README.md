# 发布说明归档

每个版本对应一个文件，按 `v{major}.{minor}.{patch}.md` 命名。

---

## 📋 发版规则

### 1. 发版前

- [ ] **先写发版说明**：创建 `docs/release-notes/v{X.Y.Z}.md`，包含改动要点和数据统计
- [ ] **更新 README**：在 `docs/release-notes/README.md` 版本表中追加新版本行
- [ ] **检查 `build-release.ps1` 依赖**：确认 `docs/release-notes/v{X.Y.Z}.md` 存在

### 2. 发版流程

```bash
# 1. 提交所有改动
git add -A && git commit -m "v{X.Y.Z} — 标题"

# 2. 打标签（必须与发版说明文件名一致）
git tag v{X.Y.Z}

# 3. 构建并发布到 GitHub Releases
.\build-release.ps1 v{X.Y.Z}
```

### 3. 经验教训

| 教训 | 说明 |
|------|------|
| 🏷️ **先写文档再打标签** | `build-release.ps1` 会自动读取 `docs/release-notes/v{X.Y.Z}.md` 作为 Release 正文，缺文件则用默认描述 |
| 📝 **一次性提交所有改动** | 避免多次小提交后需要补写中间版本的发版说明（如 v1.7.2→v1.8.4 间缺了 8 个版本） |
| 📊 **标注改动统计** | 每个发版说明应有修改文件数/增删行数，便于快速评估版本体积 |
| 🔄 **累积版本可合并** | 如果中间版本未单独发布，发版说明应汇总所有改动，而非只写最后一个 commit（如 v1.8.4 涵盖 v1.7.2→v1.8.4） |
| 🐙 **gh CLI 发布** | 脚本用 `gh release create` 发布，需提前 `gh auth login` 或在环境变量 `GH_TOKEN` 中配置 token |
| ⏭️ **-SkipUpload 用于测试** | 本地测试构建加 `-SkipUpload`，确认无误后再正式发布 |
| 🧹 **清理调试日志** | 发布前检查 console.log / fmt.Printf 等调试代码（见 `docs/pending-cleanup.md`） |
| 🎯 **按实际发行版本写说明** | 如果存在"试发布→正式发布"的版本跳跃，正式版本的发版说明应汇总全部累积改动 |
